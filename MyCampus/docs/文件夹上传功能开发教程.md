## 1. 背景与需求分析

### 1.1 业务场景

在校园墙项目中，已有单文件上传接口 `POST /api/resource/upload`。现在用户希望能**一次性上传整个文件夹**里的多个学习资料（如一个课程的多个章节PDF），系统需要：

- 一次上传生成一个**批次号**，方便后续按批次查询和管理
- 每个文件仍然是 `resource` 表中的一条独立记录
- **部分文件失败不影响其他文件**（部分成功策略）
- 不破坏已有的单文件上传功能

### 1.2 技术约束

| 约束项 | 限制值 | 原因 |
|--------|--------|------|
| 最大文件数 | 100 | 防止单次请求过大导致超时 |
| 单文件最大 | 50MB | 与单文件上传保持一致 |
| 总大小上限 | 500MB | Spring Boot 默认限制 + OSS 带宽考量 |
| 文件类型 | pdf/doc/docx | 与现有资料模块保持一致 |
| 接口基准路径 | `/api/resource` | 复用现有 ResourceController |

### 1.3 涉及的技术栈

- **框架**：Spring Boot 3.5.14
- **持久层**：MyBatis 3.0.3 + PageHelper
- **数据库**：MySQL 8.0
- **文件存储**：阿里云 OSS
- **认证**：JWT（jjwt 0.12.6）
- **Java 版本**：17

## 2. 架构设计概览

### 2.1 分层架构

```text
┌─────────────────────────────────────────────────┐
│  Controller 层                                   │

│  → 基础参数校验 → 调用 Service → 根据 status 组装 Result  │
├─────────────────────────────────────────────────┤
│  Service 层                                      │
│  ResourceServiceImpl.uploadFolder()              │
│  → 业务校验 → 生成批次号 → 批次入库 → 逐文件上传 → 汇总结果  │
├─────────────────────────────────────────────────┤
│  Mapper 层                                       │
│  ResourceMapper + ResourceUploadBatchMapper      │
│  → insertResource / insertBatch / updateBatchResult │
├─────────────────────────────────────────────────┤
│  数据库                                          │
│  resource 表（扩展） + resource_upload_batch 表（新增）  │
└─────────────────────────────────────────────────┘
```

### 2.2 数据流

```text
前端 FormData
   │
   ├── folderName: "高等数学复习资料"
   ├── description: "..."
   ├── files: [file1.pdf, file2.docx, ...]
   └── relativePaths: ["第一章/重点.pdf", "第二章/习题.docx", ...]
        │
        ▼
Controller: 校验 folderName/files/relativePaths 非空，数量匹配
        │
        ▼
Service:
   1. 业务校验（文件数、大小、类型、路径安全）
   2. 生成 batchNo（RB202606260001）
   3. 写入 resource_upload_batch（status=0 处理中）
   4. 遍历每个文件：
      ├── 上传到 OSS → resources/20260626/{userId}/{batchNo}/{uuid}-文件名
      ├── 写入 resource 表（uploadType=folder, batchNo=xxx）
      ├── 成功 → successRecords
      └── 失败 → failedFiles（不回滚已有成功的）
   5. 更新 batch 最终状态
        │
        ▼
Controller: 根据 status 决定 Result.code
  status=1（全部成功）→ code=200
  status=2（部分成功）→ code=200（message 区分）
  status=3（全部失败）→ code=400
```

## 3. 数据库设计

### 3.1 设计思路

采用「**批次表 + 资料表扩展**」的方式：

- **`resource_upload_batch`**：记录一次文件夹上传的整体情况（汇总统计、状态）
- **`resource`**：仍是前端资料列表的主表，每个文件一条记录
- 通过 `batch_no` 字段将同一批次上传的多个文件关联起来

### 3.2 新增表 `resource_upload_batch`

```sql
CREATE TABLE IF NOT EXISTS resource_upload_batch (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    batch_no        VARCHAR(32) NOT NULL COMMENT '批次号，格式 RB+yyyyMMdd+4位序号',
    user_id         BIGINT NOT NULL COMMENT '上传用户ID',
    folder_name     VARCHAR(255) NOT NULL COMMENT '根文件夹名称',
    description     VARCHAR(500) DEFAULT NULL COMMENT '批次描述',
    total_count     INT NOT NULL DEFAULT 0 COMMENT '文件总数',
    success_count   INT NOT NULL DEFAULT 0 COMMENT '成功上传数',
    fail_count      INT NOT NULL DEFAULT 0 COMMENT '失败数',
    total_size      BIGINT NOT NULL DEFAULT 0 COMMENT '总大小（字节）',
    status          TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0-处理中 1-全部成功 2-部分成功 3-全部失败',
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    UNIQUE KEY uk_batch_no (batch_no),
    INDEX idx_user_id (user_id),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='资料文件夹上传批次表';
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 自增主键 |
| `batch_no` | VARCHAR(32) | 批次号，全局唯一，格式 `RB202606260001` |
| `user_id` | BIGINT | 上传者，关联 `user` 表 |
| `folder_name` | VARCHAR(255) | 前端传入的根文件夹名称 |
| `description` | VARCHAR(500) | 整个批次的描述（可选） |
| `total_count` | INT | 本次上传的文件总数 |
| `success_count` | INT | 实际上传成功的数量 |
| `fail_count` | INT | 上传失败的数量 |
| `total_size` | BIGINT | 所有文件的总字节数 |
| `status` | TINYINT | 最终状态（见下表） |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 自动更新的时间 |

**status 状态枚举：**

| 值 | 含义 | 触发条件 |
|----|------|----------|
| 0 | 处理中 | 批次刚创建，文件正在上传 |
| 1 | 全部成功 | successCount == totalCount |
| 2 | 部分成功 | 0 < successCount < totalCount |
| 3 | 全部失败 | successCount == 0 |

### 3.3 扩展 `resource` 表

```sql
ALTER TABLE resource
    ADD COLUMN upload_type VARCHAR(20) NOT NULL DEFAULT 'single' COMMENT '上传类型：single/folder',
    ADD COLUMN batch_no VARCHAR(32) DEFAULT NULL COMMENT '文件夹上传批次号',
    ADD COLUMN folder_name VARCHAR(255) DEFAULT NULL COMMENT '所属根文件夹名称（仅 folder 上传时）',
    ADD COLUMN relative_path VARCHAR(500) DEFAULT NULL COMMENT '文件在文件夹内的相对路径（仅 folder 上传时）';

CREATE INDEX idx_resource_batch_no ON resource(batch_no);
```

**设计要点：**

- `upload_type` 默认值为 `'single'`，保证已有数据不受影响
- `batch_no` 为 NULL 表示该记录来自单文件上传
- `relative_path` 存储前端传入的相对路径，**仅用于展示**，不参与 OSS 存储路径构建

### 3.4 完整迁移脚本

迁移脚本已保存在 `src/main/resources/migration-folder-upload.sql`，可直接在 MySQL 中执行。

## 4. 前后端对接协议

### 4.1 请求信息

| 项目 | 说明 |
|------|------|
| 请求方式 | `POST` |
| 请求路径 | `/api/resource/upload/folder` |
| Content-Type | `multipart/form-data` |
| 是否需要登录 | 是（`Authorization: Bearer {token}`） |

### 4.2 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `folderName` | String | 是 | 根文件夹名称 |
| `description` | String | 否 | 整个上传批次的描述，最长 500 字 |
| `files` | MultipartFile[] | 是 | 文件数组，与 relativePaths 一一对应 |
| `relativePaths` | String[] | 是 | 文件在文件夹内的相对路径数组 |

> **前端注意**：`relativePaths[i]` 必须是 `files[i]` 对应的文件在文件夹内的路径，例如 `第一章/第一章重点.pdf`。后端不做真实的目录创建，仅将其存入数据库用于展示。

### 4.3 返回结构

#### 全部成功（code=200）

```json
{
  "code": 200,
  "message": "文件夹上传成功",
  "data": {
    "batchNo": "RB202606260001",
    "folderName": "高等数学复习资料",
    "totalCount": 8,
    "successCount": 8,
    "failCount": 0,
    "totalSize": 18602496,
    "status": 1,
    "records": [
      {
        "id": 101,
        "title": "第一章重点",
        "fileType": "pdf",
        "fileSize": 2048576,
        "folderName": "高等数学复习资料",
        "relativePath": "第一章/第一章重点.pdf",
        "batchNo": "RB202606260001",
        "createTime": "2026-06-26 22:30:00"
      }
    ],
    "failedFiles": []
  }
}
```

#### 部分成功（code=200）

```json
{
  "code": 200,
  "message": "文件夹上传完成，部分文件失败",
  "data": {
    "batchNo": "RB202606260001",
    "folderName": "高等数学复习资料",
    "totalCount": 8,
    "successCount": 6,
    "failCount": 2,
    "totalSize": 18602496,
    "status": 2,
    "records": [ /* 成功的 6 条 */ ],
    "failedFiles": [
      {
        "fileName": "附录.exe",
        "relativePath": "工具/附录.exe",
        "reason": "仅支持上传pdf/doc/docx文件"
      }
    ]
  }
}
```

#### 全部失败（code=400）

```json
{
  "code": 400,
  "message": "文件夹上传失败",
  "data": null
}
```

> **关键兼容原则**：前端响应拦截器只把 `code === 200` 视为成功，所以部分成功必须返回 `code=200`。区分方式是通过 `message` 字段和 `failCount`。

### 5.3 Result 统一响应扩展

在 `Result.java` 中新增一个带 `data` 参数的 `error` 重载：

```java
// 位置：vo/Result.java
// 在已有的 error(int, String) 方法之后添加

public static <T> Result<T> error(int code, String message, T data) {
    Result<T> result = new Result<>();
    result.setCode(code);
    result.setMessage(message);
    result.setData(data);
    return result;
}
```

> **为什么需要这个重载？** 部分成功时需要返回 code=200 但同时 message 是"文件夹上传完成，部分文件失败"，此时用 `Result.success(vo)` 然后 `setMessage()` 即可。但全部失败时需要 code=400 且 data=null，用现有的 `error(int, String)` 即可。

```java
import com.wang.mycampus.pojo.ResourceUploadBatch;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

@Mapper

                          @Param("failCount") Integer failCount,
                          @Param("status") Integer status);

    /** 查询今日最大批次号，用于生成下一个序号 */
    String selectMaxBatchNoForToday(@Param("prefix") String prefix);
}
```

#### 5.4.2 新建 `ResourceUploadBatchMapper.xml`


#### 5.5.2 修改 `ResourceServiceImpl.java`

##### ① 注入新依赖

```java
/** 批次号生成锁，保证同 JVM 内线程安全 */
```

##### ③ 实现文件夹上传方法（核心）

完整的 `uploadFolder` 方法分为 7 个阶段：

```
Phase 1: 参数校验
├── folderName 非空
├── files 非空
├── relativePaths 非空
├── files.length == relativePaths.length
├── files.length <= 100
├── 总大小 <= 500MB
└── 逐文件基础校验 + relativePath 安全校验

Phase 2: 生成批次号
└── generateBatchNo() → "RB202606260001"

Phase 3: 写入批次记录
└── insertBatch(status=0 处理中)

Phase 4: 逐文件上传
├── for each file:
│   ├── 上传到 OSS
│   ├── 写入 resource 表
│   ├── 成功 → successRecords
│   └── 失败 → failedFiles（catch 异常，不中断循环）

Phase 5: 判定最终状态
├── 全部成功 → status=1
├── 部分成功 → status=2
└── 全部失败 → status=3

Phase 6: 更新批次记录
└── updateBatchResult(batchNo, successCount, failCount, status)

Phase 7: 组装返回 VO
└── return ResourceFolderUploadResultVO
```

**关键代码：逐文件 try-catch 部分成功**

```java
for (int i = 0; i < files.length; i++) {
    MultipartFile file = files[i];
    String relativePath = relativePaths[i];

    try {
        // 校验 → 上传 OSS → 入库
        // ...
        successRecords.add(itemVO);
        successCount++;
    } catch (Exception e) {
        // 关键：捕获异常但不中断循环，记录失败后继续处理下一个
        log.warn("文件上传失败: {}", file.getOriginalFilename(), e);
        FailedUploadFileVO failedVO = new FailedUploadFileVO();
        failedVO.setFileName(file.getOriginalFilename());
        failedVO.setRelativePath(relativePath);
        failedVO.setReason(e.getMessage());
        failedFiles.add(failedVO);
        failCount++;
    }
}
```

##### ④ 批次号生成（线程安全）

```java
private String generateBatchNo() {
    synchronized (batchNoLock) {
        String todayPrefix = "RB" + LocalDate.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"));
        String maxBatchNo = batchMapper.selectMaxBatchNoForToday(todayPrefix);

        int nextSeq;
        if (maxBatchNo == null || maxBatchNo.isEmpty()) {
            nextSeq = 1;
        } else {
            String seqStr = maxBatchNo.substring(todayPrefix.length());
            nextSeq = Integer.parseInt(seqStr) + 1;
        }

        if (nextSeq > 9999) {
            throw new BaseException(500, "今日上传批次已达上限(9999)，请明日再试");
        }

        return todayPrefix + String.format("%04d", nextSeq);
    }
}
```

**设计说明：**
- 使用 `synchronized` 保证同 JVM 内线程安全
- 查询 `MAX(batch_no) WHERE batch_no LIKE 'RB20260626%'` 拿到当天最大序号
- 序号从 0001 开始，每天重置
- 上限 9999，超过抛异常（正常情况一天不可能超过）

##### ⑤ 路径安全校验

```java
private void validateRelativePath(String relativePath, int index) {
    if (relativePath == null || relativePath.trim().isEmpty()) {
        throw new BaseException(400, "第" + (index + 1) + "个文件的relativePath不能为空");
    }

    String path = relativePath.trim();

    if (path.contains("..")) {   // 防止目录穿越
        throw new BaseException(400, "第" + (index + 1) + "个文件的relativePath包含非法字符'..'");
    }
    if (path.contains("\\")) {   // 防止 Windows 路径分隔符
        throw new BaseException(400, "第" + (index + 1) + "个文件的relativePath包含非法字符'\\'");
    }
    if (path.startsWith("/")) {  // 防止绝对路径
        throw new BaseException(400, "第" + (index + 1) + "个文件的relativePath不能以'/'开头");
    }
}
```

> **安全要点**：`relativePath` 仅存入数据库用于前端展示，后端生成 OSS 存储路径时**完全不依赖**这个值，杜绝路径穿越攻击。

### 5.6 Controller 层：暴露 REST 接口

```java
// 位置：controller/ResourceController.java
// 新增导入
import com.wang.mycampus.vo.ResourceFolderUploadResultVO;
import java.util.List;

/*
 * 5.2 上传资料文件夹
 * */
@RequireLogin
@PostMapping("/api/resource/upload/folder")
public Result<ResourceFolderUploadResultVO> uploadFolder(
        @RequestParam("folderName") String folderName,
        @RequestParam(value = "description", required = false) String description,
        @RequestParam("files") List<MultipartFile> files,
        @RequestParam("relativePaths") List<String> relativePaths) throws IOException {

    log.info("文件夹上传 folderName={}, fileCount={}", folderName, files != null ? files.size() : 0);
    Long userId = UserContext.getUserId();

    // === Controller 层基础校验 ===
    if (folderName == null || folderName.trim().isEmpty()) {
        return Result.error(400, "文件夹名称不能为空");
    }
    if (files == null || files.isEmpty()) {
        return Result.error(400, "请选择要上传的文件夹");
    }
    if (relativePaths == null || relativePaths.isEmpty()) {
        return Result.error(400, "文件相对路径不能为空");
    }
    if (files.size() != relativePaths.size()) {
        return Result.error(400, "文件数量与路径数量不一致");
    }

    // 转换为数组传递给 Service
    MultipartFile[] fileArray = files.toArray(new MultipartFile[0]);
    String[] pathArray = relativePaths.toArray(new String[0]);

    ResourceFolderUploadResultVO vo = resourceService.uploadFolder(
            userId, folderName, description, fileArray, pathArray);

    // === 根据批次状态决定 HTTP 响应 ===
    Integer status = vo.getStatus();
    if (status != null && status == 3) {
        // 全部失败 → code=400, data=null
        return Result.error(400, "文件夹上传失败");
    } else if (status != null && status == 2) {
        // 部分成功 → code=200，但 message 特殊
        Result<ResourceFolderUploadResultVO> result = Result.success(vo);
        result.setMessage("文件夹上传完成，部分文件失败");
        return result;
    } else {
        // 全部成功 → code=200
        Result<ResourceFolderUploadResultVO> result = Result.success(vo);
        result.setMessage("文件夹上传成功");
        return result;
    }
}
```

**为什么 Controller 和 Service 都做校验？**

| 层 | 校验内容 | 原因 |
|----|----------|------|
| Controller | 参数非空、数量匹配 | 最基础的参数合法性，快速失败 |
| Service | 业务限制（大小、类型、路径安全） | 业务逻辑相关，可被其他调用方复用 |

> 这是一种**防御性编程**的实践：Controller 做"参数是否传了"的校验，Service 做"参数是否合法"的校验。

## 6. 关键设计决策

### 6.1 为什么部分成功返回 code=200？

因为前端响应拦截器代码如下：

```javascript
// 前端 axios 拦截器（示意）
if (response.data.code !== 200) {
    // 视为失败，弹出错误提示或跳转登录页
    return Promise.reject(response.data.message);
}
```

如果返回 `206`、`207` 等非 200 状态码，前端会直接将整个请求视为失败，无法展示"8 个文件成功了 6 个"的结果。

**解决方案**：
- 通过 `message` 字段区分（"文件夹上传成功" vs "文件夹上传完成，部分文件失败"）
- 通过 `failCount` 和 `failedFiles` 让前端知道哪些文件失败了

### 6.2 为什么不回滚已成功的文件？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **部分成功（采用）** | 用户体验好，重传只需传失败的文件 | OSS 上可能有"孤儿文件"（批次部分失败但文件已上传） |
| 全部回滚（事务） | 数据一致性强 | 一个文件失败导致前面所有文件白传 |

考虑到文件夹上传中单个文件失败通常是文件本身的问题（类型不支持、超大），回滚已成功文件对用户不公平，因此选择部分成功策略。

### 6.3 为什么 `relativePath` 不能用于 OSS 存储路径？

如果直接使用前端传入的 `relativePath` 作为 OSS 存储路径：

```
# 攻击者可以传入
relativePath: "../../etc/passwd"

# 如果不校验，可能导致路径穿越
```

**安全做法**：后端完全自行生成 OSS 存储路径（`resources/{yyyyMMdd}/{userId}/{batchNo}/{uuid}-文件名`），`relativePath` 仅作为展示信息存入数据库。

### 6.4 为什么批次号用 `synchronized` 而不是数据库自增？

- 数据库自增 ID 是数字，不够语义化（`RB202606260001` 一眼能看出是 6 月 26 日的第 1 个批次）
- `synchronized` 在单实例部署下足够安全
- 如果未来多实例部署，可改用 Redis 原子自增或数据库序列

## 9. 常见问题与最佳实践

### 9.1 为什么 `@RequestParam("files")` 可以接收多个文件？

Spring Boot 中，当同一个参数名出现多次时：
- 如果目标类型是 `List<MultipartFile>`，Spring 会自动把所有同名的文件收集到一个 List 中
- 如果目标类型是 `MultipartFile[]`，同样可以

前端 FormData 写法：
```javascript
const formData = new FormData();
formData.append('files', file1);  // 第一次 append
formData.append('files', file2);  // 第二次 append（同名）
// Spring 后端收到的 List<MultipartFile> 包含 [file1, file2]
```

### 9.2 如何确保 `relativePaths` 和 `files` 顺序一致？

前端在构建 FormData 时，必须保证 append 的顺序一致：

```javascript
// 正确做法
for (let i = 0; i < files.length; i++) {
    formData.append('files', files[i]);
    formData.append('relativePaths', relativePaths[i]);
}
```

后端通过数组下标索引保证对应关系：`files[i]` ↔ `relativePaths[i]`。

### 9.3 如果 OSS 上传成功但数据库插入失败怎么办？

当前实现中，OSS 上传和数据库插入在同一个 try-catch 块中：

```java
try {
    ossClient.putObject(...);   // OSS 上传
    resourceMapper.insertResource(...);  // 数据库插入
    successRecords.add(itemVO);
} catch (Exception e) {
    // 将整个文件标记为失败
    failedFiles.add(...);
}
```

如果 OSS 上传成功但数据库插入失败：
- 异常被 catch，该文件被记录为失败
- OSS 上会留下一个"孤儿文件"（无法通过 resource 表找到）

**改进思路**（暂未实施，留给读者思考）：
- 可以记录一个待清理列表，上传完成后异步删除
- 或使用 OSS 生命周期策略自动清理未关联的文件

### 9.4 多实例部署时批次号会冲突吗？

当前使用 JVM 级别的 `synchronized` 锁，在**单实例**部署下线程安全。

如果未来需要多实例部署，可以将批次号生成改为：
- **方案A**：使用 Redis `INCR` 原子操作
- **方案B**：使用数据库的 `SELECT ... FOR UPDATE` 行锁
- **方案C**：雪花算法 + 日期前缀

### 9.5 为什么要在 Controller 和 Service 都做校验？

这是**防御性编程**的实践：

```text
Controller 层：检查参数是否"传了"
  ├── folderName 为空了吗？
  ├── files 传了吗？
  └── files 和 relativePaths 数量一致吗？

Service 层：检查参数是否"合法"
  ├── 文件类型是 pdf/doc/docx 吗？
  ├── 单个文件超过 50MB 了吗？
  ├── 总大小超过 500MB 了吗？
  └── relativePath 包含非法字符吗？
```

这样如果未来有其他地方（定时任务、消息队列）调用 `ResourceService.uploadFolder()`，业务校验依然生效。

### 9.6 单文件上传和文件夹上传的 OSS 路径有什么区别？

| 上传方式 | OSS 路径格式 | 示例 |
|----------|-------------|------|
| 单文件 | `resources/{userId}/{uuid}.{ext}` | `resources/1001/a1b2c3.pdf` |
| 文件夹 | `resources/{yyyyMMdd}/{userId}/{batchNo}/{uuid}-{文件名}` | `resources/20260626/1001/RB202606260001/d4e5f6-第一章重点.pdf` |

区别在于文件夹上传多了一层**日期目录**和**批次号目录**，方便 OSS 控制台上按日期和批次管理文件。
