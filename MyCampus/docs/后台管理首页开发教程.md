## 1. 背景与需求分析

### 1.1 业务场景

在校园墙项目中，需要为管理员提供一个**数据看板首页**，使用 ECharts 直观展示平台的运营数据，包括：

1. **概览统计卡片**：用户总数、帖子总数、资料总数、下载总次数
2. **趋势折线图**：近 7/30 天的用户注册、发帖、资料上传趋势
3. **文件类型饼图**：pdf/doc/docx 的占比分布
4. **热门资料排行**：下载量 Top10
5. **文件夹上传统计**：成功/部分成功/失败批次数
6. **最新批次列表**：最近上传的文件夹批次

### 1.2 技术约束

| 约束项 | 限制值 | 原因 |
|--------|--------|------|
| 访问权限 | 仅管理员（role=1） | 运营数据不应暴露给普通用户 |
| days 参数 | 仅支持 7 或 30 | 固定 ECharts 展示周期 |
| limit 参数 | 最大 20 | 防止一次性拉取过多数据 |
| 趋势补 0 | 必须补齐空日期 | 折线图不能有断点 |
| 统计字段 | 不返回 null | 前端不需要判空 |

## 3. 权限设计

### 3.1 背景

现有项目中已有：
- `@RequireLogin` 注解：标记需要登录的接口
- `LoginInterceptor`：检查 JWT Token 并解析用户信息到 `UserContext`
- 用户角色字段：`user.role`（0=普通用户，1=管理员）

但 `LoginInterceptor` 只检查"是否登录"，不检查"是否是管理员"。

### 3.2 设计方案

新增 `@RequireAdmin` 注解，在 `LoginInterceptor` 中增加角色校验逻辑：

```text
请求进入 → LoginInterceptor.preHandle()
  │
  ├── 方法有 @RequireAdmin？
  │   ├── 是 → 解析JWT → 获取userId → 查role
  │   │        ├── role == 1 → 放行
  │   │        └── role != 1 → 返回 403 "仅管理员可访问后台"
  │   └── 否 → 继续检查 @RequireLogin（原有逻辑不变）
  │
  └── 两者都没有 → 放行
```

**关键点：** `@RequireAdmin` 隐含了登录要求——标记了 `@RequireAdmin` 的方法不需要再标记 `@RequireLogin`。

### 3.3 代码实现

#### 3.3.1 新建注解

```java
// annotation/RequireAdmin.java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireAdmin {
}
```

#### 3.3.2 在 UserMapper 中添加角色查询

```java
// mapper/UserMapper.java（注解方式，无需 XML）
@Select("SELECT role FROM user WHERE id = #{userId}")
Integer selectRoleByUserId(@Param("userId") Long userId);
```

#### 3.3.3 修改 LoginInterceptor

```java
// 注入 UserMapper
@Autowired
private UserMapper userMapper;

// 在 preHandle 中：
// 1. 检查 @RequireAdmin（新增）
boolean requireAdmin = handlerMethod.hasMethodAnnotation(RequireAdmin.class);
// 2. 检查 @RequireLogin（原有）
boolean requireLogin = handlerMethod.hasMethodAnnotation(RequireLogin.class);
// 3. 都不需要则放行
if (!requireAdmin && !requireLogin) { return true; }

// ... JWT 解析后 ...

// 9. 如果是管理员接口，额外校验角色
if (requireAdmin) {
    Integer role = userMapper.selectRoleByUserId(userId);
    if (role == null || role != 1) {
        response.setStatus(403);
        response.getWriter().write("{\"code\":403,\"message\":\"仅管理员可访问后台\"}");
        return false;
    }
}
```

## 5. 开发步骤

### 5.1 权限体系：@RequireAdmin 注解 + 拦截器改造

详见 [第3节](#3-权限设计)。

**为什么选择注解 + 拦截器，而不是在每个 Controller 方法里判断角色？**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 每个方法里判断 | 灵活 | 代码重复，容易遗漏 |
| **注解 + 拦截器（采用）** | 统一鉴权，不易遗漏 | 拦截器耦合了 UserMapper |

注解 + 拦截器方案更符合 Spring 的 AOP 思想，维护性更好。

### 5.3 Mapper 层：数据统计 SQL

#### 5.3.1 扩展 UserMapper

```java
// 查询用户总数
@Select("SELECT COUNT(*) FROM user")
Long selectUserCount();

// 用户注册趋势 —— SQL 在 XML 中
List<TrendItemVO> selectUserRegisterTrend(@Param("days") Integer days);
```

**UserMapper.xml**：

```xml
<select id="selectUserRegisterTrend" resultType="com.wang.mycampus.vo.TrendItemVO">
    SELECT DATE(create_time) AS date, COUNT(*) AS count
    FROM user
    WHERE create_time >= DATE_SUB(CURDATE(), INTERVAL #{days} - 1 DAY)
    GROUP BY DATE(create_time)
    ORDER BY date
</select>
```

> **SQL 解释**：`DATE_SUB(CURDATE(), INTERVAL #{days} - 1 DAY)` 计算起始日期。例如 days=7 时，从 6 天前到今天（含今天共 7 天）。`DATE(create_time)` 提取日期部分，忽略时分秒。

#### 5.3.2 扩展 PostMapper

```java
List<TrendItemVO> selectPostPublishTrend(@Param("days") Integer days);
```

**PostMapper.xml**：同上，将 `user` 改为 `post`。

#### 5.3.3 扩展 ResourceMapper

```java
// 总下载次数
@Select("SELECT IFNULL(SUM(download_count), 0) FROM resource")
Long selectTotalDownloadCount();

// 上传趋势（XML）
List<TrendItemVO> selectResourceUploadTrend(@Param("days") Integer days);

// 文件类型分布（XML）
List<FileTypeDistributionVO> selectFileTypeDistribution();

// 热门资料 Top（XML）
List<HotResourceVO> selectDownloadTop(@Param("limit") Integer limit);
```

**ResourceMapper.xml**：

```xml
<select id="selectFileTypeDistribution" resultType="com.wang.mycampus.vo.FileTypeDistributionVO">
    SELECT LOWER(file_type) AS fileType, COUNT(*) AS count
    FROM resource
    GROUP BY LOWER(file_type)
    ORDER BY count DESC
</select>

<select id="selectDownloadTop" resultType="com.wang.mycampus.vo.HotResourceVO">
    SELECT id, title, download_count AS downloadCount, file_type AS fileType
    FROM resource
    ORDER BY download_count DESC, create_time DESC
    LIMIT #{limit}
</select>
```

> **为什么用 `LOWER(file_type)`？** 防止数据库中存在 `PDF`、`Pdf` 等大小写不一致的数据，统一转小写后分组。

#### 5.3.4 扩展 ResourceUploadBatchMapper

```java
FolderUploadStatVO selectBatchStats();
List<LatestUploadBatchVO> selectLatestBatches(@Param("limit") Integer limit);
```

**ResourceUploadBatchMapper.xml**：

```xml
<select id="selectBatchStats" resultType="com.wang.mycampus.vo.FolderUploadStatVO">
    SELECT
        COUNT(*) AS totalBatchCount,
        IFNULL(SUM(CASE WHEN status = 1 THEN 1 ELSE 0 END), 0) AS successBatchCount,
        IFNULL(SUM(CASE WHEN status = 2 THEN 1 ELSE 0 END), 0) AS partialSuccessBatchCount,
        IFNULL(SUM(CASE WHEN status = 3 THEN 1 ELSE 0 END), 0) AS failedBatchCount
    FROM resource_upload_batch
</select>

<select id="selectLatestBatches" resultType="com.wang.mycampus.vo.LatestUploadBatchVO">
    SELECT
        b.batch_no AS batchNo,
        b.folder_name AS folderName,
        COALESCE(u.nickname, u.username) AS uploaderName,
        b.total_count AS totalCount,
        b.success_count AS successCount,
        b.fail_count AS failCount,
        b.total_size AS totalSize,
        b.status AS status,
        DATE_FORMAT(b.created_at, '%Y-%m-%d %H:%i:%s') AS createTime
    FROM resource_upload_batch b
    LEFT JOIN user u ON b.user_id = u.id
    ORDER BY b.created_at DESC
    LIMIT #{limit}
</select>
```

> **为什么用 `COALESCE(u.nickname, u.username)`？** nickname 可能为空，此时回退到 username。

#### 5.4.2 核心实现要点

**① 概览统计：聚合 4 个表的计数**

```java
@Override
public AdminDashboardOverviewVO getOverview() {
    AdminDashboardOverviewVO vo = new AdminDashboardOverviewVO();
    vo.setUserCount(userMapper.selectUserCount());
    vo.setPostCount((long) postMapper.selectSumNumber());     // Integer → Long
    vo.setResourceCount((long) resourceMapper.selectNumber()); // Integer → Long
    vo.setTotalDownloadCount(resourceMapper.selectTotalDownloadCount());
    return vo;
}
```

> **注意**：`PostMapper.selectSumNumber()` 返回 `Integer`，需要转为 `Long` 以匹配 VO 的类型。

**② 趋势补 0：解决折线图断点**

数据库只返回有数据的日期，ECharts 折线图需要连续的日期序列。在 Service 层用 Java 补齐：

```java
private List<TrendItemVO> fillZeroDates(List<TrendItemVO> dbData, int days) {
    // 1. 将 DB 数据转为 Map<date, count>
    Map<String, Long> dataMap = new LinkedHashMap<>();
    if (dbData != null) {
        for (TrendItemVO item : dbData) {
            dataMap.put(item.getDate(), item.getCount());
        }
    }

    // 2. 生成完整的日期序列（从 N 天前到今天）
    DateTimeFormatter fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd");
    LocalDate today = LocalDate.now();
    List<TrendItemVO> result = new ArrayList<>();
    for (int i = days - 1; i >= 0; i--) {
        LocalDate date = today.minusDays(i);
        String dateStr = date.format(fmt);
        TrendItemVO vo = new TrendItemVO();
        vo.setDate(dateStr);
        vo.setCount(dataMap.getOrDefault(dateStr, 0L));  // 无数据则填 0
        result.add(vo);
    }
    return result;
}
```

**处理示例**：

```text
DB 返回：                   补 0 后返回：
[date=06-24, count=3]     [date=06-20, count=0]
[date=06-25, count=5]     [date=06-21, count=0]
[date=06-26, count=2]     [date=06-22, count=0]
                          [date=06-23, count=0]
                          [date=06-24, count=3]
                          [date=06-25, count=5]
                          [date=06-26, count=2]
```

**③ 空值防御**

`selectBatchStats()` 在表为空时可能返回 `null`，需要做防御：

```java
@Override
public FolderUploadStatVO getFolderUploadStat() {

```

### 5.5 Controller 层：暴露 8 个管理端接口

```java
@Slf4j
@RestController
@RequestMapping("/api/admin/dashboard")
public class AdminDashboardController {

    @Autowired
    private AdminDashboardService adminDashboardService;

    // 6.1 概览统计
    @RequireAdmin
    @GetMapping("/overview")
    public Result<AdminDashboardOverviewVO> getOverview() {
        return Result.success(adminDashboardService.getOverview());
    }

    // 6.2 用户注册趋势
    @RequireAdmin
    @GetMapping("/user-register-trend")
    public Result<List<TrendItemVO>> getUserRegisterTrend(
            @RequestParam(defaultValue = "7") Integer days) {
        validateDays(days);
        return Result.success(adminDashboardService.getUserRegisterTrend(days));
    }

    // ... 其余 6 个接口结构类似

    // 参数校验
    private void validateDays(Integer days) {
        if (days == null || (days != 7 && days != 30)) {
            throw new BaseException(400, "days 参数仅支持 7 或 30");
        }
    }
}
```

**设计要点：**

1. **所有方法都标记 `@RequireAdmin`**（不是 `@RequireLogin`），保证只有管理员能访问
2. **`days` 参数仅允许 7 或 30**，避免用户传入 365 天导致查询过慢
3. **`limit` 参数最大 20**，同样防止过大值
4. **`@RequestParam(defaultValue = "7")`** 给默认值，前端不传参数也能正常调用

## 7. 关键设计决策

### 7.1 为什么趋势补 0 在 Service 层而不是 SQL 中？

MySQL 8.0 可以用递归 CTE 生成连续日期然后 LEFT JOIN：

```sql
WITH RECURSIVE dates AS (
    SELECT CURDATE() - INTERVAL 6 DAY AS dt
    UNION ALL
    SELECT dt + INTERVAL 1 DAY FROM dates WHERE dt < CURDATE()
)
SELECT d.dt AS date, IFNULL(COUNT(u.id), 0) AS count
FROM dates d LEFT JOIN user u ON DATE(u.create_time) = d.dt
GROUP BY d.dt ORDER BY d.dt;
```

**选择 Java 补 0 的原因：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| SQL 递归 CTE | 一次查询完成 | SQL 复杂，DBA 维护成本高 |
| **Java 补 0（采用）** | SQL 简单清晰，逻辑可读 | 需要两次处理（查 DB + 补 0） |

对于 days∈{7,30} 的数据量，Java 补 0 性能完全不是问题。

### 7.2 为什么 4 个统计查询分布在 4 个 Mapper 中？

后台首页需要横跨 `user`、`post`、`resource`、`resource_upload_batch` 4 张表的统计数据。方案对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 新建 AdminDashboardMapper | 统计查询集中管理 | 增加一个类，违背按领域分 Mapper 的惯例 |
| **复用现有 Mapper（采用）** | 符合 MyBatis 按表拆分惯例 | 统计查询散落在不同 Mapper 中 |

考虑到查询都是围绕某个表展开的（用户注册趋势 → UserMapper，发帖趋势 → PostMapper），复用现有 Mapper 更自然。

### 7.3 为什么 `@RequireAdmin` 不替代 `@RequireLogin`？

`@RequireAdmin` 和 `@RequireLogin` 是两个不同权限层级：

| 注解 | 含义 | 适用场景 |
|------|------|----------|
| `@RequireLogin` | 已登录即可 | 发帖、上传、点赞 |
| `@RequireAdmin` | 需管理员 | 后台首页、用户管理 |

如果让 `@RequireAdmin` 替代 `@RequireLogin`，会把所有需要登录的普通接口也变成管理员接口，这显然不合理。所以两者并存，`@RequireAdmin` 额外增加角色校验。

## 10. 常见问题与最佳实践

### 10.1 如何新增一个管理端接口？

1. 在对应的 Mapper 中添加查询方法
2. 在 Mapper XML 中编写 SQL
3. 在 `AdminDashboardService` 接口中声明方法
4. 在 `AdminDashboardServiceImpl` 中实现
5. 在 `AdminDashboardController` 中添加端点（**别忘了 `@RequireAdmin`**）

### 10.2 如何让某个接口对"管理员"和"登录用户"都开放？

使用 `@RequireLogin` 代替 `@RequireAdmin`，然后在方法内部调用 `UserContext.getUserId()` 获取当前用户，在 Service 层根据用户角色做不同处理。

### 10.3 趋势数据"补 0"逻辑可以复用吗？

可以。当前 `fillZeroDates` 方法是 `private` 的，如果其他模块也需要趋势补 0（如小工具箱的使用趋势），可以提取为一个工具类：

```java
public class TrendUtils {
    public static List<TrendItemVO> fillZeroDates(Map<String, Long> dataMap, int days) {
        // ... 补齐逻辑
    }
}
```

### 10.4 为什么 getOverview 中要把 Integer 转为 Long？

`PostMapper.selectSumNumber()` 返回 `Integer`，`ResourceMapper.selectNumber()` 也返回 `Integer`，但 `AdminDashboardOverviewVO` 的字段是 `Long`。

这是为了避免未来数据量增长时 `Integer` 溢出（`Integer.MAX_VALUE = 21亿`，虽然短期内不太可能，但 Long 是更好的实践）。

### 10.5 如果未来需要更多统计指标怎么办？

方案建议：
1. **小型扩展**（1-5 个新指标）：在现有 Mapper 中加方法，在 Service 中加实现
2. **中型扩展**（10+ 个 API）：拆分 Controller（如 `AdminUserController`、`AdminResourceController`）
3. **大型扩展**：引入专门的统计中间层（如定时任务生成统计快照表）

### 10.6 性能优化建议

- 当前所有统计都是**实时查询**，数据量小（<百万级别）时完全没问题
- 如果数据量增长到百万以上，建议：
  - 对趋势 SQL 中的 `create_time` 字段建立索引
  - 使用定时任务预计算统计快照（每 5 分钟或每小时）
  - 考虑引入 Redis 缓存统计结果

## 总结

本文档完整覆盖了"后台管理首页"8 个接口的：

1. **权限设计**：`@RequireAdmin` 注解 + `LoginInterceptor` 角色校验

核心设计思想：
- **注解驱动权限**：`@RequireAdmin` → 拦截器统一鉴权
- **字段不返回 null**：空列表返回 `[]`，统计返回 0
- **趋势补齐**：折线图不能有断点
- **statusText 后端组裝**：前端直接显示，减少沟通成本
