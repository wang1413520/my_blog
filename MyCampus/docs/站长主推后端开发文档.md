# 站长主推后端开发文档

## 一、文档说明

### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属项目 | 校园墙后端 |
| 模块名称 | 资源模块 - 站长主推 |
| 技术栈 | Spring Boot + MyBatis + MySQL + JWT |
| 接口基础路径 | `http://localhost:8080/api/featured-resource` |
| 认证方式 | `Authorization: Bearer {token}` |
| 文档版本 | v1.0 |
| 创建日期 | 2026-07-06 |

### 1.2 开发目标

在现有公共资源 `resource` 表不增加字段的前提下，新增“站长主推”能力，用于：

- 将已有资源加入“站长主推”专区
- 支持主推资源独立排序、上下线和备注说明
- 支持前台按“站长主推”单独查询列表
- 支持后台新增、删除、修改主推配置

本次方案核心原则：

- 不修改现有 `resource` 表结构
- 不复制资源文件本体，不重复存储文件信息
- 通过单独新表与 `resource.id` 建立关联
- 下载仍复用原有资源下载接口

## 二、方案总览

### 2.1 为什么单独建表

你当前不希望在原有 `resource` 表中增加 `is_featured`、`section` 等字段，因此“站长主推”更适合设计成独立推荐表。

这样做的好处：

- 不污染原资源主表
- 主推逻辑和普通资源逻辑职责分离
- 后续可扩展主推文案、排序值、封面、上下线状态
- 如果某个资源取消主推，只删映射关系即可

### 2.2 推荐采用“映射表”方案

推荐不要新建一张完整复制资源信息的表，而是新建一张“主推配置表”，只保存：

- 关联的资源 `resource_id`
- 主推说明
- 排序值
- 是否启用
- 可选封面图

资源标题、描述、文件大小、下载地址等，查询时仍从 `resource` 表获取。

## 三、数据表设计

### 3.1 新增表 `featured_resource`

```sql
CREATE TABLE featured_resource (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    resource_id     BIGINT NOT NULL COMMENT '关联资源ID',
    featured_title  VARCHAR(255) DEFAULT NULL COMMENT '主推标题，可为空，为空时取资源标题',
    featured_desc   VARCHAR(500) DEFAULT NULL COMMENT '主推说明，可为空，为空时取资源描述',
    cover_url       VARCHAR(500) DEFAULT NULL COMMENT '主推封面图，可选',
    sort            INT NOT NULL DEFAULT 0 COMMENT '排序值，越大越靠前',
    status          TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0-停用 1-启用',
    created_by      BIGINT DEFAULT NULL COMMENT '创建人ID',
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    UNIQUE KEY uk_resource_id (resource_id),
    KEY idx_status_sort (status, sort),
    KEY idx_created_by (created_by)
) COMMENT='站长主推资源表';
```

### 3.2 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键 |
| resource_id | BIGINT | 对应 `resource.id` |
| featured_title | VARCHAR(255) | 自定义主推标题 |
| featured_desc | VARCHAR(500) | 自定义主推描述 |
| cover_url | VARCHAR(500) | 自定义封面图 |
| sort | INT | 排序值，建议越大越靠前 |
| status | TINYINT | 0 停用，1 启用 |
| created_by | BIGINT | 操作人 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

### 3.3 设计说明

- `resource_id` 唯一，表示一个资源最多被主推一次
- `featured_title`、`featured_desc` 允许为空，便于复用原资源标题和描述
- `cover_url` 允许为空，前端可回退为原资源封面
- `status` 用于上下线控制，避免频繁删除数据

### 3.4 是否需要外键

如果当前项目数据库管理比较简单，可以先不加物理外键，只在业务层校验 `resource_id` 是否存在。

如果你们后端规范较严格，也可以增加：

```sql
ALTER TABLE featured_resource
ADD CONSTRAINT fk_featured_resource_resource_id
FOREIGN KEY (resource_id) REFERENCES resource(id);
```

## 六、后台管理接口协议

### 6.1 新增主推资源

- 请求方式：`POST`
- 请求路径：`/api/featured-resource`
- 是否需要登录：是
- 是否需要管理员：是

请求体建议：

```json
{
  "resourceId": 101,
  "featuredTitle": "Spring Boot 毕设资料主推",
  "featuredDesc": "站长精选，资料完整，适合课程设计与毕业设计参考",
  "coverUrl": "https://xxx.com/cover/featured-101.png",
  "sort": 100,
  "status": 1
}
```

业务校验：

- `resourceId` 必填
- 对应资源必须存在
- 同一个 `resourceId` 不能重复加入主推
- `sort` 可为空，默认 0

### 6.2 修改主推资源

- 请求方式：`PUT`
- 请求路径：`/api/featured-resource/{id}`

请求体建议：

```json
{
  "featuredTitle": "更新后的主推标题",
  "featuredDesc": "更新后的主推说明",
  "coverUrl": "https://xxx.com/cover/new.png",
  "sort": 80,
  "status": 1
}
```

说明：

- 不建议允许修改 `resourceId`
- 如果要换资源，删除后重新新增更清晰

### 6.3 删除主推资源

- 请求方式：`DELETE`
- 请求路径：`/api/featured-resource/{id}`

说明：

- 删除的是主推关系，不删除原资源文件
- 删除后原资源仍然存在于普通资源列表中

### 6.4 后台查询主推列表

- 请求方式：`GET`
- 请求路径：`/api/featured-resource/admin/list`

建议请求参数：

| 参数名 | 类型 | 必填 | 说明 |
|------|------|------|------|
| page | int | 否 | 页码 |
| size | int | 否 | 每页大小 |
| keyword | string | 否 | 标题/描述/资源标题搜索 |
| status | int | 否 | 0 停用，1 启用 |

## 九、Controller 设计建议

### 9.1 接口定义示例

```java
@RestController
@RequestMapping("/api/featured-resource")
public class FeaturedResourceController {

    @GetMapping("/list")
    public Result<PageVO<FeaturedResourceVO>> getFeaturedList(FeaturedResourceQueryDTO queryDTO) {
        return Result.success(featuredResourceService.getFeaturedList(queryDTO));
    }

    @GetMapping("/admin/list")
    public Result<PageVO<FeaturedResourceVO>> getAdminFeaturedList(FeaturedResourceQueryDTO queryDTO) {
        return Result.success(featuredResourceService.getAdminFeaturedList(queryDTO));
    }

    @GetMapping("/{id}")
    public Result<FeaturedResourceVO> getDetail(@PathVariable Long id) {
        return Result.success(featuredResourceService.getDetail(id));
    }

    @PostMapping
    public Result<Void> add(@RequestBody FeaturedResourceAddDTO dto, HttpServletRequest request) {
        Long userId = JwtUtil.getUserId(request);
        featuredResourceService.add(dto, userId);
        return Result.success();
    }

    @PutMapping("/{id}")
    public Result<Void> update(@PathVariable Long id, @RequestBody FeaturedResourceUpdateDTO dto) {
        featuredResourceService.update(id, dto);
        return Result.success();
    }

    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) {
        featuredResourceService.delete(id);
        return Result.success();
    }
}
```

### 9.2 权限建议

- 前台 `GET /list` 可匿名访问
- 后台新增、修改、删除、管理列表，建议仅管理员可访问
- 如果当前项目已有管理员注解或拦截器，直接复用

## 十、Service 设计建议

### 10.1 方法签名建议

```java

PageVO<FeaturedResourceVO> getAdminFeaturedList(FeaturedResourceQueryDTO queryDTO);

void update(Long id, FeaturedResourceUpdateDTO dto);

void delete(Long id);
```

### 10.2 新增主推流程

建议流程：

1. 校验 `resourceId` 是否存在
2. 校验该资源是否已被加入主推
3. 组装 `FeaturedResource`
4. 写入数据库

### 10.3 查询列表流程

建议流程：

1. 查询 `featured_resource`
2. 关联 `resource` 表
3. 关联用户表拿上传者昵称
4. 组装 `FeaturedResourceVO`
5. 按 `sort DESC, id DESC` 排序返回

### 10.4 删除流程

只删除 `featured_resource` 中的记录：

- 不删 `resource`
- 不删文件
- 不影响资源下载

## 十一、Mapper / SQL 设计建议

### 11.1 主推列表查询 SQL 思路

```sql
SELECT
    fr.id,
    fr.resource_id,
    COALESCE(fr.featured_title, r.title) AS title,
    COALESCE(fr.featured_desc, r.description) AS description,
    fr.cover_url,
    r.file_type,
    r.file_size,
    r.download_count,
    u.nickname AS uploader_name,
    fr.created_at AS create_time,
    fr.sort,
    fr.status
FROM featured_resource fr
LEFT JOIN resource r ON fr.resource_id = r.id
LEFT JOIN user u ON r.user_id = u.id
WHERE fr.status = 1
ORDER BY fr.sort DESC, fr.id DESC;
```

### 11.2 后台管理列表可扩展条件

可增加：

- `fr.status = #{status}`
- `title like`
- `description like`
- `resource.title like`

### 11.3 新增前校验 SQL

```sql
SELECT COUNT(1)
FROM featured_resource
WHERE resource_id = #{resourceId};
```

### 11.4 校验资源是否存在

```sql
SELECT COUNT(1)
FROM resource
WHERE id = #{resourceId};
```

## 十二、接口兼容性约束

由于当前前端响应拦截器一般只接受 `code === 200`，因此建议后端保持：

- 查询成功：`code = 200`
- 新增成功：`code = 200`
- 修改成功：`code = 200`
- 删除成功：`code = 200`

错误场景建议：

- 主推资源不存在：`404`
- 关联资源不存在：`400`
- 重复加入主推：`400`
- 无权限操作：`401 / 403`

## 十三、与现有资源模块的关系

### 13.1 复用点

- 文件下载：复用 `GET /api/resource/download/{id}`
- 文件封面：继续复用资源页原有文件类型封面逻辑
- 文件信息：复用 `resource` 表已有字段

### 13.2 不复用点

- 不复用原资源上传接口作为“主推新增”
- 不在 `resource` 表增加主推字段
- 不把主推逻辑写死在 `GET /api/resource/list`

### 13.3 是否在公共资源接口中增加参数

首版不建议在 `GET /api/resource/list` 上加 `featured=true`。

原因：

- “普通资源列表”和“站长主推列表”语义不同
- 单独接口职责更清晰
- 前端路由和页面结构也已经拆成二级栏目

## 十四、测试清单

后端联调前建议至少验证：

1. 新增主推时，`resourceId` 存在可成功写入
2. 重复新增同一个 `resourceId` 会被拦截
3. 删除主推只删除映射关系，不影响原资源
4. 停用状态的数据前台不返回
5. 前台列表按 `sort DESC` 正确排序
6. 主推标题为空时，前台能回退到原资源标题
7. 主推描述为空时，前台能回退到原资源描述
8. 原资源被删除后，主推数据如何处理要有明确策略

### 14.1 关于“原资源被删除”的建议

推荐两种做法二选一：

- 方案 A：删除原资源前，先检查是否被主推，若被主推则不允许删除
- 方案 B：删除原资源后，同时清理对应 `featured_resource` 记录

首版更推荐方案 A，规则更清晰，避免前台出现失效主推。

---

## 十五、推荐实现结论

本次“站长主推”后端最推荐方案如下：

- 新建 `featured_resource` 表
- 表中只存主推配置，不复制资源文件本体
- 通过 `resource_id` 关联现有 `resource` 表
- 前台单独走 `GET /api/featured-resource/list`
- 后台单独走主推增删改查接口
- 下载继续复用原 `resource` 模块

这样既满足“单独建表”，也能最大限度复用现有资源系统能力，整体改动最小、结构最清晰。
