# 学习资料上传文件夹后端开发文档

## 一、文档说明

### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属项目 | 校园墙后端 |
| 模块名称 | 学习资料 |
| 技术栈 | Spring Boot 3 + MyBatis + MySQL |
| 接口基础路径 | `http://localhost:8080/api/resource` |
| 认证方式 | JWT Token（`Authorization: Bearer {token}`） |
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-26 |

### 1.2 开发目标

在现有单文件上传接口 `POST /api/resource/upload` 不变的前提下，新增“上传资料文件夹”能力，供前端一次上传一个目录内的多个资料文件。

核心要求：

- 新增接口与现有资源模块风格一致
- 一次文件夹上传生成一个批次
- 文件夹内每个文件最终仍落成一条独立资料记录
- 支持部分成功，不因单个文件失败导致整批回滚
- 与前端文档字段完全一致

## 三、前后端对接协议

这一节必须与前端文档保持一致。

### 3.1 请求信息

- 请求方式：`POST`
- 请求路径：`/api/resource/upload/folder`
- Content-Type：`multipart/form-data`
- 是否需要登录：是

### 3.2 请求参数

| 参数名 | 类型 | 必填 | 说明 |
|------|------|------|------|
| folderName | string | 是 | 根文件夹名称 |
| description | string | 否 | 整个上传批次描述，最长 500 字 |
| files | MultipartFile[] | 是 | 文件数组 |
| relativePaths | String[] | 是 | 与 `files` 顺序一一对应的相对路径数组 |

### 3.3 文件类型规则

首版与现有资料模块保持一致，仅支持：

- `pdf`
- `doc`
- `docx`

### 3.4 返回结构

```json
{
  "code": 200,
  "message": "文件夹上传成功",
  "data": {
    "batchNo": "RB202606260001",
    "folderName": "高等数学复习资料",
    "totalCount": 8,
    "successCount": 8,
    "failCount": 0,
    "totalSize": 18602496,
    "records": [
      {
        "id": 101,
        "title": "第一章重点",
        "fileType": "pdf",
        "fileSize": 2048576,
        "folderName": "高等数学复习资料",
        "relativePath": "第一章/第一章重点.pdf",
        "batchNo": "RB202606260001",
        "createTime": "2026-06-26 22:30:00"
      }
    ],
    "failedFiles": []
  }
}
```

### 3.5 关键兼容约束

当前前端响应拦截器只把 `code === 200` 视为成功，因此后端必须遵守：

- 全部成功：返回 `code = 200`
- 部分成功：仍返回 `code = 200`
- 全部失败：才返回非 `200`

区分方式：

- `message`：成功 / 部分成功
- `failCount`：失败数
- `failedFiles`：失败明细

不要返回 `206`、`207` 让前端自行判断，否则会被当前拦截器直接当作失败。

## 四、数据库设计

推荐采用“批次表 + 资料表扩展字段”的方式。

### 4.1 新增批次表 `resource_upload_batch`

```sql
CREATE TABLE resource_upload_batch (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    batch_no        VARCHAR(32) NOT NULL UNIQUE COMMENT '上传批次号',
    user_id         BIGINT NOT NULL COMMENT '上传用户ID',
    folder_name     VARCHAR(255) NOT NULL COMMENT '根文件夹名称',
    description     VARCHAR(500) DEFAULT NULL COMMENT '批次描述',
    total_count     INT NOT NULL DEFAULT 0 COMMENT '文件总数',
    success_count   INT NOT NULL DEFAULT 0 COMMENT '成功数',
    fail_count      INT NOT NULL DEFAULT 0 COMMENT '失败数',
    total_size      BIGINT NOT NULL DEFAULT 0 COMMENT '总大小，单位字节',
    status          TINYINT NOT NULL DEFAULT 0 COMMENT '0-处理中 1-全部成功 2-部分成功 3-全部失败',
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_user_id (user_id),
    INDEX idx_batch_no (batch_no)
) COMMENT='资料文件夹上传批次表';
```

### 4.2 扩展现有 `resource` 表

在现有 `resource` 表上新增以下字段：

```sql
ALTER TABLE resource
ADD COLUMN upload_type VARCHAR(20) NOT NULL DEFAULT 'single' COMMENT '上传类型：single/folder',
ADD COLUMN batch_no VARCHAR(32) DEFAULT NULL COMMENT '文件夹上传批次号',
ADD COLUMN folder_name VARCHAR(255) DEFAULT NULL COMMENT '所属根文件夹名称',
ADD COLUMN relative_path VARCHAR(500) DEFAULT NULL COMMENT '文件夹内相对路径';
```

### 4.3 设计说明

- `resource_upload_batch` 用于记录一次文件夹上传的整体情况
- `resource` 仍是前端资料列表的主表
- 文件夹中的每个文件独立占用一条 `resource` 记录
- 通过 `batch_no` 将多个文件归为同一次上传

## 七、Controller 设计

### 7.1 接口定义

```java
@PostMapping("/upload/folder")
public Result<ResourceFolderUploadResultVO> uploadFolder(
        @RequestParam("folderName") String folderName,
        @RequestParam(value = "description", required = false) String description,
        @RequestParam("files") MultipartFile[] files,
        @RequestParam("relativePaths") List<String> relativePaths,
        HttpServletRequest request) {
    return Result.success(resourceService.uploadFolder(folderName, description, files, relativePaths, request));
}
```

### 7.2 Controller 层校验

Controller 至少做以下基础校验：

- `folderName` 不能为空
- `files` 不能为空
- `relativePaths` 不能为空
- `files.length == relativePaths.size()`

如不满足，直接返回：

```json
{
  "code": 400,
  "message": "请求参数不合法",
  "data": null
}
```

## 八、业务规则

### 8.1 上传限制

| 校验项 | 规则 |
|------|------|
| 文件数 | 最多 100 个 |
| 单文件大小 | 不超过 50MB |
| 总大小 | 不超过 500MB |
| 文件类型 | 仅支持 `pdf/doc/docx` |
| 相对路径 | 不允许为空 |
| 路径安全 | 不允许 `..`、`\`、绝对路径 |

### 8.2 标题生成规则

每个文件落库时：

- `title`：取文件名去掉扩展名
- `fileType`：取扩展名并转小写
- `folderName`：取前端传入值
- `relativePath`：取前端传入值
- `uploadType`：固定为 `folder`

示例：

| 原文件名 | title | fileType |
|------|------|------|
| `第一章重点.pdf` | `第一章重点` | `pdf` |
| `期末提纲.docx` | `期末提纲` | `docx` |

### 8.3 部分成功策略

一次文件夹上传中：

- 单个文件失败时，不回滚已成功文件
- 成功文件照常入库
- 失败文件记录到 `failedFiles`
- 批次状态根据最终结果写入

批次状态建议：

| status | 说明 |
|------|------|
| 1 | 全部成功 |
| 2 | 部分成功 |
| 3 | 全部失败 |

## 九、Service 处理流程

### 9.1 总体流程

```text
1. 获取当前登录用户
2. 校验 folderName / files / relativePaths
3. 生成 batchNo
4. 计算 totalCount / totalSize
5. 先写入 resource_upload_batch（status=0）
6. 遍历 files 与 relativePaths
7. 单文件校验
8. 上传文件到存储（本地或 OSS）
9. 写入 resource 记录
10. 累计 successCount / failCount
11. 汇总 failedFiles
12. 更新 resource_upload_batch 最终状态
13. 组装返回 VO
```

### 9.2 伪代码示例

```java
public ResourceFolderUploadResultVO uploadFolder(
        String folderName,
        String description,
        MultipartFile[] files,
        List<String> relativePaths,
        HttpServletRequest request) {

    Long userId = getCurrentUserId(request);
    validateFolderUpload(folderName, files, relativePaths);

    String batchNo = generateBatchNo();
    long totalSize = Arrays.stream(files).mapToLong(MultipartFile::getSize).sum();

    ResourceUploadBatch batch = createBatch(userId, batchNo, folderName, description, files.length, totalSize);
    resourceUploadBatchMapper.insert(batch);

    List<ResourceFolderItemVO> successRecords = new ArrayList<>();
    List<FailedUploadFileVO> failedFiles = new ArrayList<>();

    for (int i = 0; i < files.length; i++) {
        MultipartFile file = files[i];
        String relativePath = relativePaths.get(i);

        try {
            validateSingleFile(file, relativePath);
            Resource resource = saveResourceFile(userId, batchNo, folderName, description, file, relativePath);
            successRecords.add(toFolderItemVO(resource));
        } catch (Exception ex) {
            failedFiles.add(buildFailedFile(file.getOriginalFilename(), relativePath, ex.getMessage()));
        }
    }

    updateBatchFinalStatus(batch, successRecords.size(), failedFiles.size());

    return buildResult(batchNo, folderName, totalSize, successRecords, failedFiles);
}
```

## 十、文件存储建议

### 10.1 OSS / 本地目录结构

建议按批次号存储：

```text
resource/
  2026/06/26/
    10001/
      RB202606260001/
        1f2a3b4c-第一章重点.pdf
        6d7e8f9a-期末提纲.docx
```

组成建议：

- 日期目录：便于归档
- 用户目录：便于隔离
- 批次目录：便于定位同一次上传
- 最终文件名：`UUID + 原始文件名`

### 10.2 安全要求

- 不要直接使用 `relativePath` 作为真实存储路径
- `relativePath` 仅用于展示和入库
- 存储路径必须由后端自行生成
- 过滤路径穿越字符，如 `..`、`:`、`\`

## 十四、联调验收标准

满足以下条件即可认为后端开发完成：

1. 单文件上传接口不受影响
2. `POST /api/resource/upload/folder` 可正常接收 `folderName + files + relativePaths`
3. 能正确生成批次号 `batchNo`
4. 文件夹内每个成功文件都能写入 `resource` 表
5. 批次汇总能写入 `resource_upload_batch` 表
6. 部分成功时返回 `code = 200`
7. `records` 与 `failedFiles` 字段结构和前端文档一致
8. `GET /api/resource/list` 能兼容返回 `uploadType/folderName/relativePath/batchNo`

## 十五、推荐实现结论

本次后端最稳妥的方案是：

- 新增 `POST /api/resource/upload/folder`
- 新增 `resource_upload_batch` 批次表
- 扩展 `resource` 表记录文件夹来源信息
- 每个文件单独处理、单独入库
- 整批请求支持部分成功
- 对前端始终保持 `Result<T>` 且部分成功返回 `code: 200`

这样既能和现有资料列表页直接对接，也不会破坏你当前已经完成的单文件上传能力。
