# 评论楼中楼（多级回复）前后端开发文档

> 目标：实现 B 站式的嵌套评论。C 既能评论文章，也能回复 B 的评论，还能回复 B 评论里的回复 D（楼中楼）。
> 约束：**不改原 `comment` 表结构**，新增一张 `comment_reply` 表承载所有"回复"。原表、原接口、存量数据零迁移。

---

## 一、整体方案

| 内容 | 存储位置 | 说明 |
|---|---|---|
| 顶层评论（直接评文章） | 原 `comment` 表 | 完全不动，现有逻辑、分页、`commentCount` 全部保留 |
| 楼中楼（回复别人的评论） | 新 `comment_reply` 表 | 所有"评论之评论"都进这张表 |

**为什么这样拆：**
- 顶层评论是分页主体（`page / size` 管顶层条数），用原表不用改任何现有查询。
- 楼中楼通过 `root_comment_id` 挂到某条顶层评论下，一次 SQL 就能把某帖子的全部回复捞出并按根分组。
- 回滚容易：删掉新表即可，老功能完全不受影响。

---

## 二、数据表设计（新增一张表）

### 2.1 DDL

```sql
CREATE TABLE comment_reply (
    id                BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    post_id           BIGINT       NOT NULL COMMENT '所属帖子ID（冗余，便于直接按帖子查+防串楼校验）',
    root_comment_id   BIGINT       NOT NULL COMMENT '挂在哪条顶层评论下（comment 表的id），顶层评论之间不串楼',
    parent_id         BIGINT       DEFAULT NULL COMMENT '直接回复的评论id：NULL=直接回复顶层评论；否则=另一条回复的id',
    user_id           BIGINT       NOT NULL COMMENT '回复人ID',
    reply_to_user_id  BIGINT       DEFAULT NULL COMMENT '被@的用户ID：直接回复顶层评论时为NULL；回复某人时=被回复人ID',
    content           VARCHAR(500) NOT NULL COMMENT '回复内容，不超过500字',
    status            TINYINT      NOT NULL DEFAULT 1 COMMENT '状态：1-正常 0-已删除（软删）',
    create_time       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    KEY idx_post_root (post_id, root_comment_id),
    KEY idx_root (root_comment_id),
    KEY idx_parent (parent_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评论回复（楼中楼）表';
```

### 2.2 字段语义说明

- `root_comment_id`：**必填**，值 = 被回复的那条顶层评论在 `comment` 表的 `id`。
  - 作用一：楼中楼只渲染在对应顶层评论下面；
  - 作用二：删除顶层评论时用它批量级联删回复；
  - 作用三：`list` 接口按它分组，避免递归。
- `parent_id`：可选。
  - `NULL` → "直接回复顶层评论"（B 直接评 A 的文章，A 的这条评论在 comment 表）。
  - 有值 → "回复楼中楼里的某条回复"（C 回复 B，或 C 回复 D），值 = `comment_reply.id`（注意不是 comment 表的 id）。
  - **约定：`parent_id` 永远指向楼中楼表里的记录，`root_comment_id` 永远指向顶层评论表里的记录。**
- `reply_to_user_id`：被@的人。直接回复顶层评论时可留 `NULL`（默认被回复人=顶层评论作者），前端展示时若为 NULL 则回退显示顶层评论作者名。

### 2.3 为什么不用无限递归树

如果每条回复都允许继续挂子级（`parent_id` 指向任意评论），前端要递归渲染、分页和"展开/收起"都会复杂得多。**本方案做 B 站式两级：**
- 顶层评论（comment 表）
- 楼中楼（comment_reply 表，全部平铺在该顶层评论下）
- 楼中楼里再回复别人时，**仍然平铺**，只是显示"回复 @某某"

这样一次 `IN` 查询即可取回全部回复，无需递归。

## 三、后端改动

### 3.1 新增实体 `CommentReply.java`

```java
package com.campus.entity;

import lombok.Data;
import java.time.LocalDateTime;

@Data
public class CommentReply {
    private Long id;
    private Long postId;
    private Long rootCommentId;
    private Long parentId;
    private Long userId;
    private Long replyToUserId;
    private String content;
    private Integer status;      // 1正常 0已删除
    private LocalDateTime createTime;
}
```

### 3.2 新增请求 DTO `AddCommentDTO`（改造）

原 DTO 仅 `postId / content`，新增两个可选字段：

```java
public class AddCommentDTO {
    private Long postId;
    private String content;      // 不超过500字
    private Long parentId;       // 新增，可选：楼中楼里被直接回复的 comment_reply.id
    private Long replyToUserId;  // 新增，可选：被@的用户ID
}
```

> 注意：`parentId` 的语义**必须**在文档和代码里统一——它指向 `comment_reply.id`。前端传值时不要和 `root_comment_id` 混淆。

### 3.3 新增返回 VO `CommentReplyItemVO.java`

```java
public class CommentReplyItemVO {
    private Long id;
    private Long postId;
    private Long rootCommentId;
    private Long parentId;
    private Long replyToUserId;
    private String replyToUserName;   // 被@的人名（NULL 时前端回退为顶层评论作者名）
    private String authorName;        // 回复人名字
    private String authorAvatar;      // 回复人头像
    private String content;
    private String createTime;
    private Boolean isOwner;          // 当前登录用户是否本人（前端控制删除按钮）
}
```

### 3.4 接口约定

#### (1) 发表评论 `POST /api/comment/add`（改造）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| postId | long | 是 | 帖子ID |
| content | string | 是 | 内容 ≤500字 |
| parentId | long | 否 | 有值=走楼中楼；为空=走原 comment 表 |
| replyToUserId | long | 否 | 被@用户ID |

**后端处理流程：**

1. **鉴权**：需登录，取当前登录用户ID。
2. **内容校验**：非空、≤500字。
3. **分支判断**：
   - `parentId == null` → 写入原 `comment` 表（`postId / userId / content`），**与现在完全一致**，`rootCommentId` 无值。
   - `parentId != null` → 写入 `comment_reply` 表：
     - 查询 `comment_reply` 的 `parentId` 记录；查不到报错"回复的评论不存在"。
     - 取其 `postId` 与当前请求 `postId` 比对，不一致报错"不能跨帖子回复"（防串楼）。
     - 取该记录的 `root_comment_id` 作为新记录的 `root_comment_id`；若该记录本身就是顶层回复（`parent_id IS NULL`），则 `root_comment_id = parentId` 的记录自身的 `root_comment_id`。
     - `reply_to_user_id`：传了就存；没传则取被直接回复那条记录的作者 `user_id`（保证"回复 @某人"永远有名字）。
4. **成功返回**：新记录ID（顶层返回 comment.id，楼中楼返回 comment_reply.id）。

> ⚠️ 校验顺序很重要：**先查 `parentId` 是否存在，再比对 `postId`**。防止用户传入别的帖子的 `parentId` 造成串楼。

#### (2) 获取评论列表 `GET /api/comment/list`（改造）

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| postId | long | 是 | 帖子ID |
| page | int | 否 | 页码（按顶层评论分页） |
| size | int | 否 | 每页顶层评论数，默认20 |

**返回结构（顶层带 children）：**

```json
{
  "code": 200,
  "data": {
    "records": [
      {
        "id": 1,
        "postId": 10,
        "content": "我也觉得，希望学校能改善一下",
        "authorName": "王五",
        "authorAvatar": "https://...",
        "createTime": "2024-01-15 16:00:00",
        "isOwner": false,
        "children": [
          {
            "id": 101,
            "postId": 10,
            "rootCommentId": 1,
            "parentId": null,
            "replyToUserId": null,
            "replyToUserName": "王五",
            "authorName": "张三",
            "authorAvatar": "https://...",
            "content": "顶一下",
            "createTime": "2024-01-15 17:00:00",
            "isOwner": true
          }
        ]
      }
    ],
    "total": 15,
    "page": 1,
    "size": 20
  }
}
```

**后端处理流程：**

1. 分页查顶层评论：`WHERE post_id = ?`，按 `create_time DESC`（或现有排序），`page/size` 照旧。**这段 SQL 一行不改。**
2. 拿到本页顶层评论 id 集合 `rootIds`。
3. 一次查询全部楼中楼：`SELECT * FROM comment_reply WHERE post_id = ? AND root_comment_id IN (rootIds) AND status = 1 ORDER BY create_time ASC`。
4. 在内存里按 `root_comment_id` 分组，挂到对应顶层评论的 `children`。
5. 组装 VO：`authorName / authorAvatar` 联查 `user` 表；`replyToUserName` 联查被@用户；`isOwner` 由当前登录用户判断。

> ⚠️ 楼中楼排序建议 `create_time ASC`（楼层顺序），顶层评论用原排序。分页只作用于顶层，楼中楼一页内全量带回（可设上限 50 条防超大帖）。

#### (3) 删除评论 `DELETE /api/comment/{id}`（改造）

- **删除顶层评论**：保持原逻辑删 `comment` 表记录 + 新增级联：`DELETE FROM comment_reply WHERE root_comment_id = #{id}`（或软删 `status=0`）。
- **删除楼中楼回复**：URL 参数区分不了顶层/楼中楼（id 可能撞号）。**建议：**
  - 方案一（推荐）：新增接口 `DELETE /api/comment/reply/{id}`，删除 `comment_reply` 记录，仅本人可删。
  - 方案二：老接口里判断 `id` 属于哪张表，两张表都查——实现绕，**不推荐**。

> ⚠️ 权限：无论删顶层还是删回复，都校验 `user_id = 当前登录用户ID`，管理员可删任意。删除回复不影响同楼其他回复（软删则内容显示"已删除"，保留楼层）。

## 四、前端改动（PostDetail.vue 评论区）

### 4.1 接口封装 `src/api/comment.js`

```js
export const commentAPI = {
  addComment(data) { return request.post('/comment/add', data) },          // data 增加 parentId / replyToUserId
  getCommentList(params) { return request.get('/comment/list', { params }) }, // 返回 records，每项含 children
  deleteComment(id) { return request.delete(`/comment/${id}`) },            // 删顶层
  deleteCommentReply(id) { return request.delete(`/comment/reply/${id}`) }  // 新增，删楼中楼
}
```

### 4.2 数据结构与渲染（两层 v-for）

`comments` 每项含 `children` 数组：

```html
<div v-for="comment in comments" :key="comment.id" class="comment-item">
  <!-- 顶层评论：头像 / 作者+吉祥物 / 内容 / 时间 / [回复][删除] -->
  <div class="comment-reply-area" v-if="comment.children?.length">
    <div v-for="reply in comment.children" :key="reply.id" class="reply-item">
      <!-- 楼中楼：缩进 + 小头像 / 作者 回复 @某人 / 内容 / [回复][删除] -->
    </div>
  </div>
</div>
```

### 4.3 回复交互

1. 每条评论（含楼中楼回复）加「回复」按钮。
2. 点击后设置 `replyTarget = { id, userId, name }`，**在该评论下方就地展开**输入框：
   - `el-input` + 发布按钮，placeholder 显示 `回复 @{{ replyTarget.name }}`。
   - 顶部大输入框逻辑不变（`parentId` 为空 = 评论文章）。
3. 发布：`commentAPI.addComment({ postId, content, parentId: replyTarget.id, replyToUserId: replyTarget.userId })`。
   - **注意**：`parentId` 传的是被回复记录在各自表中的 id —— 顶层评论被回复时传 `comment.id`；楼中楼被回复时传 `reply.id`（comment_reply.id）。**前端自己记录即可，后端根据 parentId 是否存在自动分流。**
4. 成功后**局部刷新**：重新拉一次 `getCommentList`（简单可靠），或后端返回新记录后 push 进对应 `children`。

### 4.4 展示细节

- 楼中楼：`padding-left: 20px`，浅色背景条 `#f8fafc`，头像 28px，缩进明显。
- 楼中楼作者行：`张三 回复 @王五`，被@的人名高亮（`#5f9fe0`）。
- 顶层评论被回复人默认是文章作者：当 `replyToUserName` 为空时显示文章作者名。
- 删除：`isOwner` 或管理员才显示删除按钮，顶层走 `deleteComment`，楼中楼走 `deleteCommentReply`，删除前 `ElMessageBox.confirm` 二次确认。

## 五、注意事项（汇总）

### 5.1 数据一致性
1. **`root_comment_id` 必须从被回复记录继承**，不能由前端传来直接信任，后端校验后用查到的值。
2. **`parent_id` 与 `root_comment_id` 的指向不同**：前者→comment_reply 表，后者→comment 表，实现和注释里都要写清，防止混用。
3. 删除顶层评论**必须级联清理回复**，否则出现"悬空楼中楼"（孤儿数据）。
4. 楼中楼查不到 `parentId` 时要报错，**先查存在、再比对 postId**。

### 5.2 权限
5. 评论/回复都需要登录；删除仅本人或管理员。
6. 校验 `reply_to_user_id` 是否真实用户，防止伪造 @。

### 5.3 性能
7. 楼中楼一次 `IN` 查询带回，不要逐条查（N+1）。
8. 分页只作用于顶层，楼中楼建议设单顶层回复上限（如 50 条），超出提示"查看全部回复"（二期可做展开/收起）。
9. 给 `comment_reply` 建好 `(post_id, root_comment_id)` 联合索引。

### 5.4 兼容性
10. 存量老评论没有 children，前端 `comment.children?.length` 判空即可，老数据照常显示。
11. 顶层评论的 `commentCount`（帖子详情头部的评论数）**建议包含回复数**：`comment表计数 + comment_reply表计数`，二选一在前端或后端汇总，避免数字对不上。
12. 回滚方案：后端删新表、前端恢复 `comment.js` 和评论区即可，原功能不受影响。

## 六、实施顺序建议

1. **后端**：建表 → `CommentReply` 实体 → `AddCommentDTO` 加字段 → `add` 接口分流写入 → `list` 接口组装 children → 删除接口（新增 `DELETE /comment/reply/{id}`）。
2. **前端**：`comment.js` 加方法 → `PostDetail.vue` 改成两层渲染（先能显示楼中楼）→ 加回复按钮 + 就地输入框交互。
3. **联调**：按上文返回结构对字段名（`children / replyToUserName / isOwner` 等），用 Postman/接口文档核对。
