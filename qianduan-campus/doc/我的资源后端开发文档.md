# 我的资源后端开发文档

## 一、文档说明
### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属项目 | 校园墙后端 |
| 模块名称 | 个人中心 - 我的资源 |
| 技术栈 | Spring Boot + MyBatis + MySQL + JWT |
| 接口基础路径 | `http://localhost:8080/api/resource` |
| 认证方式 | `Authorization: Bearer {token}` |
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-27 |

### 1.2 开发目标

为个人中心新增“我的资源”能力，用于查询当前登录用户上传到网站的资料列表。

本次后端改造目标：

- 不影响现有公共资源列表接口 `GET /api/resource/list`
- 新增“我的资源”专用接口
- 支持关键字、文件类型、上传类型筛选
- 兼容单文件上传与文件夹上传
- 继续复用现有删除资源接口

---

## 二、接口设计总览

### 2.1 保留现有接口

| 接口 | 说明 |
|------|------|
| `POST /api/resource/upload` | 上传单文件资源，保持不变 |
| `POST /api/resource/upload/folder` | 上传文件夹资源，保持不变 |
| `GET /api/resource/list` | 公共资源列表，保持不变 |
| `GET /api/resource/{id}` | 资源详情，保持不变 |
| `GET /api/resource/download/{id}` | 资源下载，保持不变 |
| `DELETE /api/resource/{id}` | 删除资源，保持不变 |

### 2.2 新增接口

| 接口 | 说明 |
|------|------|
| `GET /api/resource/my/list` | 查询当前登录用户上传的资源列表 |

说明：

- “我的资源”只需要查询能力即可
- 删除继续复用 `DELETE /api/resource/{id}`
- 下载继续复用 `GET /api/resource/download/{id}`

---

## 三、接口协议
### 3.1 查询我的资源列表

- 请求方式：`GET`
- 请求路径：`/api/resource/my/list`
- 是否需要登录：是

请求参数建议：

| 参数名 | 类型 | 必填 | 说明 |
|------|------|------|------|
| page | int | 否 | 页码，默认 1 |
| size | int | 否 | 每页大小，默认 10 |
| keyword | string | 否 | 标题/描述关键字 |
| fileType | string | 否 | 文件类型：`pdf/doc/docx` |
| uploadType | string | 否 | 上传类型：`single/folder` |

### 3.2 返回结构

建议返回 `PageVO<ResourceItemVO>`，与现有资源列表接口尽量保持一致。

由于当前前端响应拦截器只接受 `code === 200`，因此后端必须保证：

- 查询成功返回 `code = 200`
- 空列表也返回 `code = 200`
- 不要因为“没有数据”返回 `404`

## 四、设计思路
### 4.1 为什么单独开接口

不建议直接在公共接口 `GET /api/resource/list` 上加一个 `mine=true` 参数作为首版方案，原因：

- 公共资源列表是匿名也可访问的
- “我的资源”必须依赖登录态
- 将公开列表和个人列表拆开，职责更清晰
- 更利于后续增加“我的资源统计”“我的上传批次”等能力

### 4.2 查询归属判断

“我的资源”必须严格按当前登录用户过滤：

- 不允许前端传 `userId`
- 必须从 JWT / 登录上下文中解析 `currentUserId`
- SQL 以 `resource.user_id = currentUserId` 为核心条件

---

## 五、数据表依赖
### 5.1 现有表依赖

假设当前资源表已有或应已有：

```text
resource
```

建议至少包含以下字段：

| 字段 | 说明 |
|------|------|
| id | 资源ID |
| user_id | 上传用户ID |
| title | 标题 |
| description | 描述 |
| file_type | 文件类型 |
| file_size | 文件大小 |
| download_count | 下载次数 |
| create_time | 创建时间 |

如果你已经做过文件夹上传扩展，则还应包含：

| 字段 | 说明 |
|------|------|
| upload_type | 上传类型：`single/folder` |
| folder_name | 文件夹名称 |
| relative_path | 文件夹内相对路径 |
| batch_no | 文件夹上传批次号 |

### 5.2 是否需要新建表

首版“我的资源”功能不需要新增数据表。

原因：

- 数据本身已经存在 `resource` 表
- “我的资源”只是按当前用户筛选资源记录
- 文件夹上传的批次信息也应已落在资源记录中

说明：

- 如果当前项目资源列表查询已集中在 `ResourceController/ResourceService`，就继续放在这里

## 七、DTO / VO 设计
### 7.1 查询 DTO

建议新增：

```java
public class ResourceMyListQueryDTO {
    private Integer page;
    private Integer size;
    private String keyword;
    private String fileType;
    private String uploadType;
}
```

### 7.2 返回 VO

优先复用现有 `ResourceItemVO`。

若当前 `ResourceItemVO` 已包含：

- `id`
- `title`
- `description`
- `fileType`
- `fileSize`
- `downloadCount`
- `uploaderName`
- `createTime`

则建议补充或确认以下字段：

```java
private String uploadType;
private String folderName;
private String relativePath;
private String batchNo;
```

这样前端就能直接复用当前资源页的文件夹分组展示逻辑。

---

## 八、Controller 设计
### 8.1 接口定义

```java
@GetMapping("/my/list")
public Result<PageVO<ResourceItemVO>> getMyResourceList(
        ResourceMyListQueryDTO queryDTO,
        HttpServletRequest request) {
    Long userId = JwtUtil.getUserId(request);
    return Result.success(resourceService.getMyResourceList(userId, queryDTO));
}
```

说明：

- `userId` 必须从登录态解析
- 前端不应该也不允许传 `userId`
- 接口仅返回当前用户自己的资源

---

## 九、Service 设计
### 9.1 方法签名建议

```java
PageVO<ResourceItemVO> getMyResourceList(Long userId, ResourceMyListQueryDTO queryDTO);
```

### 9.2 查询逻辑

处理流程建议：

1. 校验分页参数
2. 标准化 `keyword/fileType/uploadType`
3. 根据 `userId` 查询资源
4. 按 `create_time desc` 排序
5. 组装 `PageVO<ResourceItemVO>` 返回

### 9.3 查询条件建议

核心条件：

```sql
WHERE r.user_id = #{userId}
```

可选条件：

```sql
AND r.title LIKE CONCAT('%', #{keyword}, '%')
```

或：

```sql
AND (
  r.title LIKE CONCAT('%', #{keyword}, '%')
  OR r.description LIKE CONCAT('%', #{keyword}, '%')
)
```

文件类型：

```sql
AND r.file_type = #{fileType}
```

上传类型：

```sql
AND r.upload_type = #{uploadType}
```

排序：

```sql
ORDER BY r.create_time DESC, r.id DESC
```

### 10.2 SQL 说明

建议和现有公共资源列表 SQL 保持字段一致，只是在原查询基础上增加：

```sql
r.user_id = #{userId}
```

如果公共资源列表已经 join 用户表拿 `uploaderName`，这里也可以继续 join，保持返回结构统一。

## 十一、字段校验建议
### 11.1 分页参数

| 字段 | 规则 |
|------|------|
| page | 小于 1 时按 1 处理 |
| size | 默认 10，建议最大 50 |

### 11.2 枚举字段

| 字段 | 允许值 |

- `文件类型参数不合法`
- `上传类型参数不合法`

---

## 十二、权限要求

必须满足：

1. 只有登录用户才能访问 `GET /api/resource/my/list`
2. 只能查询当前登录用户自己的资源
3. 不允许通过请求参数指定别人的 `userId`
4. 继续保留现有删除权限校验：仅上传者本人或管理员可删除

---

## 十三、与现有删除接口的关系

当前已有：

```text
DELETE /api/resource/{id}
```

“我的资源”页删除时直接复用此接口即可。

后端需要继续保证：

- 当前资源上传者可以删除
- 管理员可以删除
- 其他普通用户不能删除

如果删除的是文件夹上传中的单个文件：

- 首版允许只删除单条资源记录
- 不强制联动删除整个批次

后续如果要支持“删除整个文件夹上传批次”，可再新增：

```text
DELETE /api/resource/batch/{batchNo}
```

但这不属于本次必做范围。

---

## 十四、与文件夹上传的兼容要求

“我的资源”必须兼容现有文件夹上传能力，因此后端查询结果中建议保留：

| 字段 | 说明 |
|------|------|
| uploadType | 单文件 / 文件夹上传 |
| folderName | 文件夹名称 |
| relativePath | 文件夹内相对路径 |
| batchNo | 同一批次标识 |

这样前端可以：

- 对 `uploadType === 'folder'` 的资源做分组
- 按 `batchNo` 构建文件夹卡片
- 按 `relativePath` 构建目录树

---

## 十五、返回结构约束

建议继续使用现有分页结构：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "records": [],
    "total": 0,
    "page": 1,
    "size": 10
  }
}
```

即使 `records` 为空，也不要返回错误。

---

## 十六、测试清单

后端完成后建议验证：

1. 未登录访问 `/api/resource/my/list` 是否返回 401
2. 登录后只返回当前用户自己的资源
3. 关键字筛选是否正常
4. 文件类型筛选是否正常
5. 上传类型筛选是否正常
6. 文件夹上传资料是否带回 `uploadType/folderName/relativePath/batchNo`
7. 空列表是否返回 `code = 200`
8. 删除接口在“我的资源”场景下是否仍可正常使用

---

## 十七、推荐开发顺序

1. 确认 `resource` 表已有 `user_id`
2. 确认 `ResourceItemVO` 是否已包含文件夹上传扩展字段
3. 新增 `ResourceMyListQueryDTO`
4. 在 `ResourceMapper` 中新增“按用户查询”SQL
5. 在 `ResourceService` 中新增 `getMyResourceList`
6. 在 `ResourceController` 中暴露 `/api/resource/my/list`
7. 联调前端个人中心“我的资源”页
