# 个人博客备忘录后端联调文档

## 一、文档说明

### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属前端项目 | `qianduan-campus` |
| 所属后端项目 | 个人博客 / 校园墙后端 |
| 模块名称 | 备忘录 `memo` |
| 文档目标 | 提供一份可直接用于前后端联调的后端实现说明 |
| 技术栈 | Spring Boot 3 + MyBatis + MySQL |
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-27 |

### 1.2 适用范围

本文档只覆盖“备忘录”模块，不覆盖文章、评论、资源、工具箱等已有模块。

### 1.3 联调目标

本次设计的目标不是做复杂待办系统，而是保证以下几点：

1. 前端首页备忘录卡片能稳定接入后端
2. 字段命名与前端现有数据结构保持一致
3. 登录态、权限、返回格式与现有项目风格兼容
4. 尽量避免时间格式、状态字段、鉴权方式导致的联调问题

---

## 二、先给结论

### 2.1 是否需要新建表

需要。

备忘录不建议复用 `post` 表，原因如下：

1. 语义不同，备忘录不是文章
2. 操作频率不同，备忘录更轻、更碎片化
3. 状态字段需求不同，需要完成状态、置顶状态
4. 后续如果增加搜索、归档、提醒，也更容易扩展

### 2.2 首版建议

首版建议采用以下最小可用方案：

1. 新建 `memo` 表
2. 所有备忘录都绑定当前登录用户
3. 前端只使用 `content`，不加 `title`
4. 支持新增、列表、修改、删除、完成/未完成切换、置顶/取消置顶
5. 后端返回字段严格使用前端当前字段名

## 三、必须对齐的前端现状

当前前端首页备忘录组件使用的数据结构为：

```json
{
  "id": 1719465600000,
  "content": "记得补接口文档",
  "status": 0,
  "isPinned": 0,
  "createTime": 1719465600000,
  "updateTime": 1719465600000
}
```

### 3.1 字段含义

| 字段 | 类型 | 含义 |
|------|------|------|
| `id` | `Long` | 备忘录主键 |
| `content` | `String` | 备忘录内容 |
| `status` | `Integer` | 完成状态，`0` 未完成，`1` 已完成 |
| `isPinned` | `Integer` | 置顶状态，`0` 未置顶，`1` 已置顶 |
| `createTime` | `Long` | 创建时间，13 位毫秒时间戳 |
| `updateTime` | `Long` | 更新时间，13 位毫秒时间戳 |

### 3.2 联调关键要求

为避免前端出现解析问题，后端请注意以下约定：

1. `status` 必须返回数字 `0/1`，不要返回 `true/false`
2. `isPinned` 必须返回数字 `0/1`，不要返回 `true/false`
3. `createTime` 和 `updateTime` 建议直接返回 13 位毫秒时间戳
4. 不建议返回 `2026-06-27 14:30:00` 这种非标准字符串时间

说明：

- 这样可以直接兼容前端当前的 `formatTime(new Date(timestamp))` 处理方式
- 可以规避不同浏览器对日期字符串解析不一致的问题

## 四、数据库设计

## 4.1 建表 SQL

```sql
CREATE TABLE memo (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  user_id BIGINT NOT NULL COMMENT '所属用户ID',
  content VARCHAR(120) NOT NULL COMMENT '备忘录内容',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '状态 0未完成 1已完成',
  is_pinned TINYINT NOT NULL DEFAULT 0 COMMENT '置顶 0否 1是',
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  KEY idx_memo_user_id (user_id),
  KEY idx_memo_user_status_pin_update (user_id, is_pinned, status, update_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户备忘录表';
```

## 4.2 字段说明

| 字段 | 说明 | 是否必须 |
|------|------|------|
| `id` | 主键 | 是 |
| `user_id` | 当前登录用户ID | 是 |
| `content` | 备忘录内容，首版最长 120 字 | 是 |
| `status` | 完成状态 | 是 |
| `is_pinned` | 置顶状态 | 是 |
| `create_time` | 创建时间 | 是 |
| `update_time` | 更新时间 | 是 |

## 4.3 首版不建议新增的字段

首版不建议加这些字段，避免联调复杂化：

- `title`
- `color`
- `remind_time`
- `is_deleted`
- `sort_order`
- `tag`

这些都可以第二阶段再扩展。

## 五、接口设计

## 5.1 鉴权约定

所有备忘录接口都要求登录后访问。

前端请求头会自动带：

```http
Authorization: Bearer <token>
```

后端要求：

1. 从登录态中解析当前用户
2. 所有查询和写操作都只能作用于当前用户自己的数据
3. 不允许通过前端传 `userId` 决定数据归属

### 5.1.1 安全要求

以下做法必须避免：

1. 前端请求体里传 `userId`
2. 后端直接信任前端传入的 `userId`
3. 根据 `id` 查到备忘录后不校验所属用户

正确做法：

1. 当前用户ID从 token 中获取
2. 所有 `select / update / delete` 都必须带上 `user_id = 当前用户ID`

---

## 5.2 统一返回格式

当前前端 `src/utils/request.js` 的成功处理逻辑要求后端继续沿用统一返回结构：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

### 5.2.1 成功响应

- HTTP 状态码：`200`
- 业务 `code`：`200`

### 5.2.2 普通业务失败建议

建议继续沿用项目现有风格：

- HTTP 状态码：`200`
- 业务 `code`：非 `200`
- `message`：给前端直接展示的中文提示

例如：

```json
{
  "code": 400,
  "message": "备忘录内容不能为空",
  "data": null
}
```

### 5.2.3 鉴权失败

鉴权失败建议使用：

- HTTP `401`：未登录或 token 失效
- HTTP `403`：无权限

这样可以直接兼容前端现有拦截器逻辑。

## 六、接口清单

## 6.1 获取备忘录列表

### 请求

```http
GET /api/memo/list
```

### 请求参数

首版建议不传参数。

如果后端想预留筛选能力，可以支持以下可选参数，但前端首版不会依赖：

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `status` | `Integer` | 否 | `0/1` |
| `isPinned` | `Integer` | 否 | `0/1` |
| `keyword` | `String` | 否 | 内容关键字 |

### 返回示例

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "id": 101,
      "content": "记得补备忘录后端文档",
      "status": 0,
      "isPinned": 1,
      "createTime": 1719465600000,
      "updateTime": 1719469200000
    },
    {
      "id": 102,
      "content": "晚上把首页再微调一下",
      "status": 1,
      "isPinned": 0,
      "createTime": 1719451200000,
      "updateTime": 1719454800000
    }
  ]
}
```

### 排序要求

后端建议默认按以下顺序返回：

1. `is_pinned desc`
2. `status asc`
3. `update_time desc`

这与前端当前排序逻辑一致。

## 八、Service / Mapper 实现约束

## 8.1 列表查询

查询必须带当前用户条件：

```sql
SELECT id, content, status, is_pinned, create_time, update_time
FROM memo
WHERE user_id = #{currentUserId}
ORDER BY is_pinned DESC, status ASC, update_time DESC
```

## 8.2 单条更新

更新必须带当前用户条件：

```sql
UPDATE memo
SET content = #{content}, update_time = NOW()
WHERE id = #{id} AND user_id = #{currentUserId}
```

## 8.3 状态更新

```sql
UPDATE memo
SET status = #{status}, update_time = NOW()
WHERE id = #{id} AND user_id = #{currentUserId}
```

## 8.4 置顶更新

```sql
UPDATE memo
SET is_pinned = #{isPinned}, update_time = NOW()
WHERE id = #{id} AND user_id = #{currentUserId}
```

## 8.5 删除

```sql
DELETE FROM memo
WHERE id = #{id} AND user_id = #{currentUserId}
```

### 8.5.1 必须校验的情况

如果更新或删除影响行数为 `0`，建议按“记录不存在或无权限”处理。

建议返回：

```json
{
  "code": 404,
  "message": "备忘录不存在",
  "data": null
}
```

## 十、前后端联调注意事项

## 10.1 不要让前端传 `userId`

备忘录归属必须由后端通过 token 决定，否则会有越权风险。

## 10.2 不要把时间返回成普通字符串

不要返回：

```text
2026-06-27 14:30:00
```

建议返回：

```text
1719473400000
```

原因：

1. 前端当前已经按时间戳在处理
2. 不同浏览器对普通日期字符串解析不稳定

## 10.3 不要把状态返回成布尔值

不要返回：

```json
{
  "status": true,
  "isPinned": false
}
```

必须返回：

```json
{
  "status": 1,
  "isPinned": 0
}
```

## 10.4 新增接口返回整条对象

新增、修改、状态更新、置顶更新后，建议都直接返回更新后的完整对象，而不是只返回 `true`。

这样前端可以直接刷新当前项，联调最省事。

## 10.5 列表接口首版不分页

首版首页备忘录是卡片式展示，数量不会太大，建议先不分页。

理由：

1. 前端接入简单
2. 联调成本低
3. 后续真要分页再扩展也不晚

---

## 十一、推荐联调顺序

建议按下面顺序联调：

1. 先打通 `GET /api/memo/list`
2. 再打通 `POST /api/memo/add`
3. 再联调 `PUT /api/memo/{id}/status`
4. 再联调 `PUT /api/memo/{id}/pin`
5. 再联调 `DELETE /api/memo/{id}`
6. 最后补 `PUT /api/memo/{id}` 内容编辑

这样最符合前端页面当前的主要交互路径。

---

## 十二、联调验收清单

后端完成后，至少要通过以下场景：

1. 登录用户能看到自己的备忘录列表
2. 用户 A 看不到用户 B 的备忘录
3. 新增备忘录成功，内容长度限制生效
4. 能切换完成/未完成状态
5. 能切换置顶/取消置顶
6. 删除后列表中不再出现该记录
7. 返回字段名与前端完全一致
8. 时间字段前端可以直接显示，不需要额外特殊处理
9. token 失效时前端会正常跳回登录页

---

## 十三、给后端同学的最终实现结论

如果目标是“前后端联调尽量不出问题”，这份备忘录模块建议严格遵守以下四条：

1. 独立新建 `memo` 表，不复用 `post`
2. 所有接口都只操作当前登录用户自己的数据
3. 返回字段固定为 `id / content / status / isPinned / createTime / updateTime`
4. `createTime / updateTime` 直接返回 13 位毫秒时间戳

只要这四条不偏，前端接接口时基本不会出大问题。
