# 我的资料后端开发文档

## 一、文档说明
### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属项目 | 校园墙后端 |
| 模块名称 | 用户中心 - 我的资料 |
| 技术栈 | Spring Boot + MyBatis + MySQL + JWT |
| 接口基础路径 | `http://localhost:8080/api/user` |
| 认证方式 | `Authorization: Bearer {token}` |
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-27 |

### 1.2 开发目标

为个人中心新增“我的资料”能力，用于存储和维护用户更完整的个人档案。该功能与现有 `/user/info`、`/user/update`、`/user/password` 分离，避免混淆账号信息与档案信息。

核心要求：

- 必须登录后才能访问
- 支持查询资料详情
- 支持新增或更新资料
- 首次未填写时也要返回成功
- 与前端字段命名保持一致

## 二、接口设计总览

### 2.1 保留现有接口

| 接口 | 说明 |
|------|------|
| `GET /api/user/info` | 查询基础用户信息，保持不变 |
| `PUT /api/user/update` | 更新昵称/头像等基础信息，保持不变 |
| `PUT /api/user/password` | 修改密码，保持不变 |

### 2.2 新增接口

| 接口 | 说明 |
|------|------|
| `GET /api/user/profile/detail` | 查询“我的资料”详情 |
| `PUT /api/user/profile/detail` | 保存“我的资料” |

## 三、前后端对接协议
### 3.1 查询资料详情

- 请求方式：`GET`
- 请求路径：`/api/user/profile/detail`
- 是否登录：是
- 请求参数：无

返回示例：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "userId": 12,
    "realName": "王思政",
    "gender": "male",
    "birthday": "2004-01-08",
    "phone": "13800138000",
    "email": "demo@example.com",
    "school": "某某大学",
    "college": "计算机学院",
    "major": "软件工程",
    "grade": "2022级",
    "location": "江苏南京",
    "bio": "喜欢前端、设计和轻量化个人站点。",
    "createTime": "2026-06-27 20:00:00",
    "updateTime": "2026-06-27 20:30:00"
  }
}
```

### 3.2 保存资料

- 请求方式：`PUT`
- 请求路径：`/api/user/profile/detail`
- 是否登录：是
- Content-Type：`application/json`

请求体示例：

```json
{
  "realName": "王思政",
  "gender": "male",
  "birthday": "2004-01-08",
  "phone": "13800138000",
  "email": "demo@example.com",
  "school": "某某大学",
  "college": "计算机学院",
  "major": "软件工程",
  "grade": "2022级",
  "location": "江苏南京",
  "bio": "喜欢前端、设计和轻量化个人站点。"
}
```

返回示例：

```json
{
  "code": 200,
  "message": "保存成功",
  "data": true
}
```

### 3.3 成功状态约束

由于当前前端响应拦截器只接受 `code === 200`：

- 查询成功必须返回 `code = 200`
- 首次未填写资料时也必须返回 `code = 200`
- 保存成功必须返回 `code = 200`

不要返回：

- `204`
- `206`
- `201`

否则当前前端会直接进入失败分支。

## 四、数据表设计
### 4.1 推荐方案

建议不要直接继续扩展 `user` 主表，而是新建一张一对一的资料扩展表：

`user_profile_detail`

优点：

- 与账号基础信息职责分离
- 便于后续继续扩展
- 降低对现有登录、注册、头像逻辑的影响

### 4.2 建表 SQL

```sql
CREATE TABLE user_profile_detail (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    user_id      BIGINT NOT NULL UNIQUE COMMENT '用户ID',
    real_name    VARCHAR(30) DEFAULT NULL COMMENT '真实姓名',
    gender       VARCHAR(10) DEFAULT NULL COMMENT '性别：male/female/unknown',
    birthday     DATE DEFAULT NULL COMMENT '出生日期',
    phone        VARCHAR(20) DEFAULT NULL COMMENT '手机号',
    email        VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
    school       VARCHAR(100) DEFAULT NULL COMMENT '学校',
    college      VARCHAR(100) DEFAULT NULL COMMENT '学院',
    major        VARCHAR(100) DEFAULT NULL COMMENT '专业',
    grade        VARCHAR(30) DEFAULT NULL COMMENT '年级',
    location     VARCHAR(100) DEFAULT NULL COMMENT '所在城市',
    bio          VARCHAR(300) DEFAULT NULL COMMENT '个人简介',
    created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    CONSTRAINT uk_user_profile_detail_user UNIQUE (user_id),
    INDEX idx_user_profile_detail_user_id (user_id)
) COMMENT='用户资料扩展表';
```

### 4.3 设计说明

- `user_id` 和 `user` 表一对一
- 首次保存时插入
- 后续保存时更新
- `bio` 限制在 300 字以内，和前端约束保持一致

## 七、Controller 设计
### 7.1 查询接口

```java
@GetMapping("/profile/detail")
public Result<UserProfileDetailVO> getProfileDetail(HttpServletRequest request) {
    Long userId = JwtUtil.getUserId(request);
    return Result.success(userProfileDetailService.getByUserId(userId));
}
```

### 7.2 保存接口

```java
@PutMapping("/profile/detail")
public Result<Boolean> updateProfileDetail(
        @RequestBody UserProfileDetailUpdateDTO dto,
        HttpServletRequest request) {
    Long userId = JwtUtil.getUserId(request);
    userProfileDetailService.saveOrUpdate(userId, dto);
    return Result.success(true);
}
```

说明：

- 用户 ID 必须从登录态中获取
- 不允许前端直接传 `userId`
- 避免越权修改其他用户资料

## 八、Service 逻辑设计
### 8.1 查询逻辑

查询流程：

1. 根据 `userId` 查询 `user_profile_detail`
2. 如果存在，组装 `VO` 返回
3. 如果不存在，返回一个空对象 `VO`
4. 返回 `code = 200`

空对象示例：

```java
new UserProfileDetailVO(
    userId,
    "", "", "", "", "", "", "", "", "", "", "",
    null,
    null
)
```

或直接手动 set 空字段，保证前端不需要额外判空分支。

### 8.2 保存逻辑

保存流程：

1. 校验 DTO 字段合法性
2. 根据 `userId` 查询资料记录
3. 如果不存在则执行 `insert`
4. 如果已存在则执行 `update`
5. 返回成功

建议方法签名：

```java
UserProfileDetailVO getByUserId(Long userId);

void saveOrUpdate(Long userId, UserProfileDetailUpdateDTO dto);
```

## 九、字段校验规则
### 9.1 后端校验建议

| 字段 | 校验规则 |
|------|----------|
| realName | 最长 30 字 |
| gender | 仅允许 `male`、`female`、`unknown` |
| birthday | 必须是合法日期 |
| phone | 允许为空；非空时必须匹配手机号格式 |
| email | 允许为空；非空时必须匹配邮箱格式 |
| school | 最长 100 字 |
| college | 最长 100 字 |
| major | 最长 100 字 |
| grade | 最长 30 字 |
| location | 最长 100 字 |
| bio | 最长 300 字 |

### 9.2 失败提示建议

| 场景 | message |
|------|---------|
| gender 非法 | `性别参数不合法` |
| birthday 非法 | `出生日期格式错误` |
| phone 非法 | `手机号格式不正确` |
| email 非法 | `邮箱格式不正确` |
| bio 超长 | `个人简介不能超过300个字符` |

## 十、Mapper 设计建议
### 10.1 基础方法

建议至少提供：

```java
UserProfileDetail selectByUserId(Long userId);

int insert(UserProfileDetail entity);

int updateByUserId(UserProfileDetail entity);
```

### 10.2 SQL 更新策略

更新时建议只更新资料字段和 `updated_at`，不要动 `created_at`。

示例思路：

```sql
UPDATE user_profile_detail
SET real_name = #{realName},
    gender = #{gender},
    birthday = #{birthday},
    phone = #{phone},
    email = #{email},
    school = #{school},
    college = #{college},
    major = #{major},
    grade = #{grade},
    location = #{location},
    bio = #{bio},
    updated_at = NOW()
WHERE user_id = #{userId}
```

## 十一、权限与安全要求

必须满足：

1. 只能操作当前登录用户自己的资料
2. `userId` 只能从 Token 中解析
3. 不允许通过请求体传入任意 `userId`
4. 对字符串字段建议做 `trim`
5. 对超长文本、非法日期、非法邮箱要拦截

如果项目中已有统一异常处理器，建议抛业务异常，由全局异常返回标准 `Result`。

## 十二、联调注意事项
### 12.1 日期格式统一

前后端统一使用：

- 查询返回：`yyyy-MM-dd`
- 保存入参：`yyyy-MM-dd`

### 12.2 空值兼容

前端允许大部分字段为空，因此后端需要支持：

- 空字符串
- `null`

建议在 Service 层统一做标准化处理：

- 空串转 `null` 或保留空串，二选一并全局一致

### 12.3 返回结构统一

保持项目现有统一返回结构：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

## 十三、测试清单

后端完成后建议验证：

1. 未登录访问资料接口是否返回 401
2. 首次查询无资料时是否正常返回 `code = 200`
3. 首次保存是否成功插入
4. 第二次保存是否成功更新
5. 非法手机号、非法邮箱、非法日期是否被拦截
6. 不同用户是否只能看到自己的资料
7. 返回字段名是否与前端文档完全一致
