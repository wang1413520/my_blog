# 个人博客后端改造文档

## 一、文档说明

### 1.1 基本信息

| 项目 | 说明 |
|------|------|
| 所属项目 | 校园墙后端 |
| 改造目标 | 用最小后端改动支撑前端改造成个人博客 |
| 技术栈 | Spring Boot 3 + MyBatis + MySQL |
| 方案定位 | 最省事方案 |
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-27 |

### 1.2 核心思路

本方案的核心不是把后端彻底重构成标准博客系统，而是：

1. 继续把 `post` 表当作“文章表”使用
2. 继续复用现有帖子、评论、用户、资料接口
3. 尽量不改数据库表结构
4. 优先保证前端能快速以“个人博客”的形态上线

---

## 二、先给结论

### 2.1 这次后端要不要大改

结论：不用大改。

### 2.2 首版后端建议

首版建议按以下原则执行：

- 不改表名
- 不改接口路径
- 不拆新模块
- 不新建文章分类表
- 不新建标签表
- 不新增封面、摘要、草稿、阅读量等字段

### 2.3 这次后端真正需要做的事

严格来说，首版甚至可以做到“后端零改动也能跑”。

但为了让前端改造更顺畅，建议做少量兼容优化。

---

## 三、现有能力复用结论

### 3.1 可直接复用的接口

| 模块 | 接口 | 用途 |
|------|------|------|
| 帖子 | `POST /api/post/publish` | 发布文章 |
| 帖子 | `GET /api/post/list` | 文章列表 |
| 帖子 | `GET /api/post/{id}` | 文章详情 |
| 帖子 | `GET /api/post/search` | 搜索文章 |
| 帖子 | `POST /api/post/like/{id}` | 点赞文章 |
| 帖子 | `DELETE /api/post/{id}` | 删除文章 |
| 评论 | `POST /api/comment/add` | 发表评论 |
| 评论 | `GET /api/comment/list` | 评论列表 |
| 评论 | `DELETE /api/comment/{id}` | 删除评论 |
| 资料 | `GET /api/resource/list` | 资源列表 |
| 用户 | 登录/获取信息/修改信息 | 作者后台能力 |

### 3.2 现有数据结构的博客映射

把现有 `post` 表理解为：

| 现有字段 | 在博客里的含义 |
|------|------|
| `id` | 文章ID |
| `title` | 文章标题 |
| `content` | 文章正文 |
| `userId` | 作者ID |
| `createTime` | 发布时间 |
| `likeCount` | 点赞数 |
| `type` | 内部兼容字段，首版不在前端展示 |
| `isAnonymous` | 内部兼容字段，首版固定用实名 |

## 四、最省事方案的边界

## 4.1 本次不做数据库升级

首版不新增：

- `category`
- `tags`
- `summary`
- `cover`
- `status`
- `slug`
- `view_count`

### 4.2 本次不做接口升级

首版不新增：

- `/api/article/*`
- `/api/category/*`
- `/api/tag/*`
- `/api/article/draft/*`

### 4.3 本次不做后台内容治理升级

首版不做：

- 评论审核
- 文章置顶
- 推荐文章
- SEO 专用字段
- 草稿箱

## 五、推荐的后端最小改动

## 5.1 方案等级说明

### 方案 A：零改动

前端提交时继续传：

```json
{
  "title": "文章标题",
  "content": "文章正文",
  "type": 1,
  "isAnonymous": 0
}
```

这种情况下，后端完全不用改。

### 方案 B：轻微优化

如果你愿意做一点点兼容优化，建议后端补下面两项。

---

## 六、建议补的两个兼容优化

## 6.1 `publishPost` 默认值兜底

### 背景

当前 `PublishPostDTO` 里包含：

- `title`
- `content`
- `type`
- `isAnonymous`

博客前端首版其实不希望再显式展示 `type` 和 `isAnonymous`。

### 建议

在后端 `publishPost` 逻辑中增加默认值处理：

```java
if (dto.getType() == null) {
    dto.setType(1);
}
if (dto.getIsAnonymous() == null) {
    dto.setIsAnonymous(0);
}
```

### 价值

- 前端以后可以少传字段
- 兼容原社区前端和新博客前端
- 改动极小

## 6.2 列表和详情接口继续兼容旧字段

### 建议

首版不要删掉这些返回字段：

- `type`
- `isAnonymous`
- `authorName`
- `authorAvatar`
- `commentCount`
- `likeCount`

### 原因

- 旧前端还能继续跑
- 新博客前端只是“不展示”，不是“不能接收”
- 可以避免一次性联动修改过多代码

---

## 七、接口层建议

## 7.1 首版接口路径全部保留

继续使用：

```text
POST   /api/post/publish
GET    /api/post/list
GET    /api/post/{id}
GET    /api/post/search
POST   /api/post/like/{id}
DELETE /api/post/{id}

POST   /api/comment/add
GET    /api/comment/list
DELETE /api/comment/{id}

GET    /api/resource/list
```

不建议首版新增 `/api/article/*` 别名接口。

原因：

- 接口别名虽然不复杂，但会带来额外维护成本
- 现阶段改名收益不大
- 前端只是展示成博客，不影响后端仍叫 `post`

## 7.2 参数校验建议

博客首版继续保留原有校验范围即可：

- 标题非空
- 内容非空
- 标题长度限制
- 内容长度限制

无需为首版新增：

- 摘要校验
- 标签校验
- 封面地址校验

---

## 八、数据库层建议

## 8.1 首版不改表结构

继续沿用现有表：

- `user`
- `post`
- `comment`
- `resource`

### 结论

不需要执行任何数据库迁移 SQL，也不需要改实体类结构。

## 8.2 数据使用约束

为了让博客前端语义更稳定，建议约定：

1. 新发布内容统一 `isAnonymous = 0`
2. 新发布内容统一固定 `type = 1` 或由后端默认填充

说明：

- `type` 只是兼容旧帖子模型
- 前端不再显示 “吐槽 / 建议”

---

## 九、Service 层建议

## 9.1 不要重命名已有 Service

首版不建议做这种改动：

- `PostService` 改成 `ArticleService`
- `PostController` 改成 `ArticleController`
- `PostMapper` 改成 `ArticleMapper`

原因：

- 代码改名成本高
- 波及面大
- 对实际上线价值不大

## 9.2 可以在注释和文档里切换语义

例如：

- 对外文档称“文章”
- 内部代码仍然保留“Post”

这是最稳妥的折中方案。

---

## 十、评论模块建议

博客首版建议完整保留评论模块。

### 原因

1. 现有评论已经可用
2. 对个人博客来说，评论是有效互动能力
3. 删除评论模块并不会显著减少后端复杂度

### 首版无需改动

- `comment` 表不动
- 评论接口不动
- 评论 VO 不动

---

## 十一、资源模块建议

资源模块可以继续作为博客的“资源分享”页使用。

### 后端是否要改

首版不用改。

### 只需要前端换语义

- “学习资料”改成“资源”
- 上传资料改成上传资源

---

## 十二、后台管理建议

当前后台首页统计的是：

- 用户总数
- 帖子总数
- 资料总数
- 下载总次数

首版可以继续保留。

### 语义调整建议

只需要在展示文案上调整：

- `帖子总数` 改成 `文章总数`
- `发帖趋势` 改成 `发文趋势`

后端统计逻辑不用改，因为本质上仍然统计 `post` 表。

---

## 十三、开发执行建议

## 13.1 后端最省事执行顺序

### 第一步

先不改任何接口，直接配合前端改造联调。

### 第二步

如果前端希望不再传 `type` 和 `isAnonymous`，再补默认值兜底。

### 第三步

联调确认以下场景正常：

1. 发布文章成功
2. 文章列表加载成功
3. 文章详情加载成功
4. 点赞成功
5. 评论成功
6. 删除文章成功

---

## 十四、验收标准

后端首版完成后，应满足：

1. 不改数据库也能支持博客前端运行
2. `/api/post/*` 全部可继续使用
3. 评论链路不受影响
4. 资料链路不受影响
5. 前端把帖子包装成文章后，接口层无需大重写

---

## 十五、第二阶段再考虑的后端升级

等博客首版稳定后，再考虑以下升级：

1. `post` 表增加 `summary`
2. `post` 表增加 `cover`
3. `post` 表增加 `status`
4. 新增 `category` 表
5. 新增 `tag` 表
6. 新增文章阅读量
7. 支持 Markdown 存储与渲染
8. 支持草稿和定时发布

---

## 十六、结论

个人博客首版最省事的后端路线是：

- 把 `post` 继续当文章用
- 保留所有现有接口路径
- 不改数据库结构
- 只做极少量默认值兼容

也就是说，这次后端不是“大改”，而是“尽量不改，必要时只做轻微兼容优化”。

这是当前项目最快、最稳、最省力的方案。
